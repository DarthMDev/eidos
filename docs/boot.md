# Booting the game's own code

eidos runs the game's real start-up, not a demo's, on the host. aletheia's
ARM9 binary is matched C end to end: every game function and every SDK
function linked into it. This document is the plan for running it, and the
contract the pieces are built against.

## What runs

The ARM9 entry point (`crt0`) calls the game's `NitroMain` at `0x02005124`
(Thumb, 180 bytes). `NitroMain` calls the system initialiser `0x02005328`
(`OS_InitTick`, `OS_InitAlarm`, `RTC_Init`, `GX_Init`, `FS_Init`, the DWC
utility arena, the power manager), then enters the frame loop.

`tools/closure.py` seeded at NitroMain reaches about 1492 matched
translation units; "Linking the boot" below is what it takes to link them
and "Running the boot" how far they run. Everything past the first overlay
load (title screen, field, battle) lives in overlays. They are matched as
well: at aletheia commit e06766e4 the overlays' game code is fully linked
(24,835 functions, 99.9993 percent of their instruction bytes) with all
3,236 of their SDK functions. What those screens wait on is the port's
wiring, not matching; `docs/title-closure.md` has the title path's detail.

`NitroMain` was not matched C in aletheia at first, so the port wrote it as
`stubs/reimpl_02005124.c` from the disassembly (`docs/title-closure.md`,
"Boot path", has the listing detail). aletheia matches it now
(`src/matched/arm9/func_02005124.c`), and the deferred buffer swap it calls
(`func_02047990.c`); with a checkout that has them the boot compiles the
matched files and leaves the two reimplementations out
(`cmake/boot.cmake`), an older checkout keeps them.

## Three layers, and where each SDK name goes

1. **Matched game code**, compiled from aletheia unchanged (portability
   rule 1). This includes most of `src/matched/arm9_sdk/`: SDK functions
   that only compute or touch memory and registers run as written.
2. **The DS address space** (`sdk/dsmem.h`, `sdk/dsmem.c`): host memory
   standing in for the DS's fixed regions, so a matched store to
   `0x04000208` lands somewhere real and the rest of the port can read it.
3. **High-level stand-ins** for what cannot run as compiled ARM code on a
   host: the CPU (CPSR, interrupt entry, thread context switch), the ARM7
   on the other end of PXI, DMA engines and the cartridge. These are port
   shims under `sdk/`, one file per SDK module, the existing convention.

The rule for a given SDK function: **compile the matched source when its
behaviour is memory and register traffic; write a shim when it depends on
the CPU or on the ARM7.** Each shim's header comment says which rule put it
there.

## Fixed addresses: the build rewrites them, aletheia does not change

3702 pointer casts in the matched corpus turn a DS address into a pointer
(`*(vu16 *)0x04000208 = 1`): 2887 into I/O, 655 into main RAM, the rest into
palette, VRAM, OAM and the shared work area. On a host those are wild
pointers.

Mapping real memory at the DS's addresses would make every one of them work,
but it is not portable as the only answer: macOS reserves the low 4 GiB of
a 64-bit process (`__PAGEZERO`) and iOS cannot lift that at all, and a fixed
mapping is a fight with ASLR everywhere else. eidos targets all of them, so
the port does it in the build. Where the host allows it (32-bit pointers,
the boot's reference), the address space is also mapped at its own
addresses at run time ("Identity mapping" below), which makes the cases no
rewrite can reach work too; the rewrite stays, so every other host runs the
same code.

`tools/dsaddr.py` copies each matched source into the build tree and
rewrites every *integer-literal-to-pointer cast whose value is in a DS
region* into

```c
((T *)bw_ds_ptr(0x04000208u))
```

`bw_ds_ptr` (in `sdk/dsmem.h`) translates a DS address into the host block
that stands for it. The rewrite is purely textual on the cast, so the
compiled code is the matched code with one function-call-shaped address in
place of a constant; nothing else moves. The same rewrite reaches casts
whose operand is a name the tool can prove holds a DS address: a file-local
`#define` of one, the parameter of a file-local register macro
(`#define REG16(a) (*(vu16 *)(a))`) whose every invocation passes one, and
the address parameter of the few SDK functions that take a register address
as a `u32` and cast it themselves (the `CALLEES` table in the tool, each
entry with its evidence).

Every DS-range literal still left alone (arithmetic, comparisons, masks,
arguments, asm operands) is classified in `docs/dsaddr-residue.md`,
generated by `python tools/dsaddr.py --report <aletheia>/src/matched -o
docs/dsaddr-residue.md`: resolved through one of the rewrites above,
harmless (a mask, a range check, a PXI word), inside an asm body, or
needing a port answer, each with its reason. A file that reaches one of the
last kind gets its port answer before it joins the build.

Literals that name a game global's own address are rewritten like any other
main-RAM literal, and reach the same byte as the global's `extern` name:
the ARM9 image's data is copied to its DS addresses in main RAM at reset and
each extern data name is bound to its address (docs/armdata.md), while the
objects `sdk/game_globals.c` and the other shims define are registered at
theirs.

## The DS address space (`sdk/dsmem.h`)

Regions the port backs with host memory, by DS address:

| DS range | What | Host backing |
|---|---|---|
| `0x02000000`-`0x02FFFFFF` | main RAM (16 MiB, TWL) | first the registry of game objects (a global defined by the port registers its DS address, so a literal cast and an `extern` name reach the same bytes), then a host block for the rest (the shared work area at `0x027FF000`/`0x02FFF000` and friends) |
| `0x03000000`-`0x03FFFFFF` | shared WRAM | 256 KiB block |
| `0x04000000`-`0x04FFFFFF` | I/O registers | a register file with read and write hooks |
| `0x05000000`-`0x050007FF` | palette RAM | 2 KiB block |
| `0x06000000`-`0x06FFFFFF` | VRAM, banked | the nine banks A-I, mapped through VRAMCNT |
| `0x07000000`-`0x070007FF` | OAM | 2 KiB block |

The register file is plain memory with optional hooks: a write hook runs
after the store (VRAMCNT remaps banks; IF is write-one-to-clear; DMA
control starts a copy), a read hook supplies live values (VCOUNT, KEYINPUT,
the IPC FIFO). The renderer reads the same registers and memory the game
wrote (DISPCNT, BGxCNT, scroll, BLDCNT, WIN, VRAM, palette, OAM), so the
picture is the game's own state, not a parallel description of it.

`sdk/dsmem.c` takes no locks and initialises nothing lazily. The game runs
one thread at a time (the run token below), so the address space is only
ever touched by the thread holding it; and `bw_ds_reset` builds every table
explicitly (regions, register file, VRAMCNT hooks, the bank mapping, the
registry with `sdk/game_globals.c`'s globals) before any game thread exists.
A translation before the first reset panics rather than initialising on
first use. A reset clears the registry and every I/O hook: a module that
registers its own objects or hooks its own registers does so again after
each reset. The approximations (flat TWL main RAM, no WRAMCNT banking, the
first bank owning a page two banks overlap) are listed in the file's header.

## Identity mapping

The rewrite reaches a DS address written as a literal. It cannot reach one
the game stores: a pointer in the ARM9 image's data or an overlay's that
aletheia's metadata does not list (the save block table at 0x0209D938 points
at 0x0209DA28, which no relocation names), a pointer the game computes
(`G2S_GetBG1CharPtr` returns `0x06200000` plus a VRAMCNT-derived offset), an
address passed as an integer. On the movable blocks every one of those is a
wild pointer, found one crash at a time.

So in a 32-bit process the port puts each region at its own DS address.
`bw_ds_identity_prepare` (called first thing by `eidos_boot`) reserves
host `0x02000000`-`0x02FFFFFF` for main RAM and the 16 MiB windows at
`0x03000000`, `0x04000000`, `0x05000000`, `0x06000000` and `0x07000000`
(`sdk/host_vm.c`'s `bw_vm_reserve_at`), and `sdk/dsmem.c` backs each region
there: main RAM committed whole, WRAM, the register file (both of its
parts), palette and OAM at their bases. Then a DS address the game holds is
the host address of its byte, and `bw_ds_ptr` is an identity outside the
registry and VRAM. Data-to-data pointers in the ARM9 image and the overlays
need no relocation; code pointers still do (docs/armdata.md).

VRAM is banked, and a host cannot alias 16 KiB pages (a Win32 view is placed
at 64 KiB granularity). So each bank the CPU can see lives at the first CPU
address VRAMCNT maps it to, in the engine windows or LCDC, and when VRAMCNT
moves it, its bytes move with it (`vram_rehome`). The renderer and the 3D
engine read banks through the same tables as before, so they see the bank
wherever it lives. Mirrors past an engine window's period are not backed: a
raw access there faults at its DS address, which the crash report names.

Windows needs one more step. A Win32 process has code-page and locale files,
heaps and user32's GDI handle table in its low addresses before `main` runs,
and with ASLR they land inside `0x02000000`-`0x08000000` often enough. When
the reservation fails, `bw_ds_identity_prepare` starts the same program again
suspended, reserves the windows in the new process before its loader runs,
waits for it and returns its exit status; the child's reservation calls take
over what the parent reserved (`BW_VM_PRERESERVED`). Linux and the BSDs do
not map there by themselves, so a reservation at start-up is enough.

The movable blocks remain the fallback, chosen at run time: an LP64 host (a
32-bit word cannot hold a host pointer anyway), a host that refuses the
ranges, a program that does not call `bw_ds_identity_prepare` (the unit
tests, which keep the banks in their stores), or `BW_DS_IDENTITY=0` in the
environment. `bw_ds_identity()` says which mode a run is in, and
`eidos_boot` prints it.

## Threads, interrupts and the frame

NitroSDK threads are preemptive only at interrupt boundaries and the game
treats them as such. The port runs each `OSThread` on a host thread under a
single run token: exactly one game thread runs at a time, and the token is
handed over where the DS would switch (`OS_SleepThread`, `OS_WakeupThread`,
`OS_YieldThread`, the end of an interrupt). That is portable (C11 threads,
pthreads, Win32), needs no assembly or `ucontext`, and keeps the game's
single-core assumptions true. Interrupts are delivered on the main thread at
the points the DS would deliver them: vblank from `engine/frame/`, timers
and alarms from `OS_GetTick`'s clock.

## Linking the boot

`-DEIDOS_BOOT=ON` links NitroMain and its closure into `eidos_boot`
(`cmake/boot.cmake`, `tools/bootlink.py`). The matched files are compiled
unchanged; what a host linker needs beyond them is generated, per build,
from aletheia's layout and the port's own sources. Everything generated
lands in `<build>/boot/`; `boot/boot_plan.txt` and
`boot/gen/boot_link_report.txt` say what was decided.

**The closure.** `tools/closure.py` reads, for each matched file, every name
it needs from elsewhere: `extern` declarations (with attributes, struct
bodies and several declarators), file-scope prototypes, and calls with no
declaration at all. A name resolves by spelling first, then by DS address
(the file's `symbols:` block, a `func_`/`sub_` spelling, the SDK table), and
an address resolves to the matched unit that defines a function there even
when the manifest lists only the unit's lead function. Names whose address
is their value (`SDK_IRQ_STACKSIZE`, `ov010_id`) are their own class,
`const`. The walk stops at the files a shim replaces, and starts again from
everything the boot's own port code calls (NitroMain's reimplementation,
`sdk/boot/`, the `stubs/reimpl_` files, the `sdk/asm/` files in place of
asm sources), until nothing new is reached. A function reached only through
a code pointer in the ARM9 data is seeded by hand (`EIDOS_BOOT_SEEDS`, with
the pointer named).

**What is left out.** Three kinds of matched file are not compiled:

- the files a port shim replaces: the single list `EIDOS_BOOT_SHIM_REPLACED`
  in `cmake/boot.cmake`, grouped by shim. The configure fails if a file in
  the closure defines a function a shim defines, by name or by address
  (`sub_02086788` in a shim and `func_02086788` in a matched file are one
  function twice), and is not on the list; a shim that only forwards to the
  address's other spelling (`sdk/aliases.c`) is a second name, not a
  replacement;
- the files whose bodies are mwcc `asm` (150 in the closure). A file
  `sdk/asm/<same name>.c` takes the place of one automatically (or the
  eidos library already has it); until it exists, every function the file
  defines is a stub;
- the files the eidos library already compiles.

**Names by address.** The DS links by address, a host by name. Each
translation unit gets a header that renames, for that file only, each
spelling to the defined one (`RTC_Init` to `func_02088788`, `func_02088610`
to the shim's `PXI_SendWordByFifo`, `func_0206074C` to
`NHTTP_CleanupAsync`), about 1647 renames in all. Any name whose DS address a
compiled source defines resolves to it: a unit's lead function by the
manifest's address (which wins over the SDK table, whose spelling of a
name can sit at another address), its other functions by their address
spellings or the SDK table. A linker veneer (`ldr ip, [pc]; bx ip` and a
target word, no source) is another address of its target: the walk follows
it and the header renames it (`tools/closure.py`, `VENEERS`). The listing
that labels the veneers is generated and is not in a clean export of the
pin, so the generators also read them out of the player's ARM9 image
(`arm9_dec.bin` beside the data root): `tools/bootlink.py` and
`tools/ovlink.py` give a veneer the boot or an overlay calls a forwarder to
its target (the overlays' named `bw_veneer_<address>`, so one unit can
declare two veneers of one target with different prototypes), and
`tools/armdata.py` treats a pointer to a veneer in the data as code. The
image also holds adjustor thunks (`ldr ip, [pc, #4]; add r0, r0, #imm;
bx ip`, the clact animation table at 0x020A7F3C points at two):
`tools/armdata.py` gives each a forwarder that moves the first argument.

**Data.** Every ARM9 data name a matched file (or the boot's port code)
uses is bound to its DS address in the player's own image
(docs/armdata.md): `tools/armdata.py` writes one `#define NAME
(*bw_dsref_NAME)` line per name, and the unit's header carries the lines
for the names that unit uses (not for a name the unit defines as a macro
itself: `TPi_TpCallback.c` says `#define tpState g_02152FA4`). A data name
the image does not bind and nothing defines fails the generation by name;
there is no zero-filled stand-in. The program installs the image with
`bw_data_install(&bw_arm9_data, 0)` before its first reset.

**Wrappers, not forced includes.** Each unit is compiled through a
generated `boot/unit/<name>.c` that includes its header and then the unit
(a matched file's dsaddr copy, or the port source). A forced include would
be a source property, which belongs to the file in every target of the
directory, and the dsaddr copies and `sdk/asm/` files are shared with tests
that compile them against their own doubles.

**Implicit declarations.** 205 callees in 103 matched files have no
declaration; mwcc compiled them as `int f()` and GCC 14 rejects them. The
header declares each as `int f()` (C99's non-prototype form, the
declaration the DS code was compiled against), or `long long f()` when its
definition returns 64 bits.

**Link-time constants** are the data layer's now (a CONST binding,
docs/armdata.md); the generator keeps its own `(*bw_lc_NAME)` form for a
constant the data header does not bind, and `bw_boot_link_init()` sets the
DS-address ones after each reset. With the current closure there are none.

**Stubs, generated and listed** in `boot_link.c`: a panicking stub for each
function nothing defines, marked `open` (game code aletheia has not
matched; an overlay function the static module calls, with the overlays
that hold its address: 0x02178E4C, ov009 or ov014) or `asm body` (waiting
for `sdk/asm/`).

`eidos_boot` links warning-free at both pointer widths and under MSVC. At
LP64 the boot's matched files raise 532 pointer/integer cast warnings,
silenced for those files only: it links, and the data layer refuses to run
it (docs/armdata.md, "Pointer width"), which `test_boot_run` checks.

## Running the boot

`eidos_boot [--data-root PATH] [--frames N] [--window] [--watchdog S]
[--screenshot N[,N...]] [--screenshot-dir DIR]` maps the address space at
its own addresses where it can (`bw_ds_identity_prepare`, "Identity
mapping"), installs the image and the overlay set, calls `bw_port_reset`
and `g3d_hw_reset`, and calls NitroMain, which never returns. Time passes
where the DS would let it: when every game thread waits, the idle thread
halts, and the OS layer's halt hook (`bw_os_set_halt_hook`) is the driver's
frame: one pass of `engine/frame/` (the tick; vblank raised through
`bw_os_raise_irq` when DISPSTAT asks for it; with `--window`, both screens
composed from the hardware state, the 3D layer from `engine/g3d/hw3d.c`),
the touch panel's automatic samples, and the sound driver's clock. The
interrupt is taken when the halt returns, the handler NitroMain installed
runs, and the waiting thread wakes. The ARM7 stand-in runs at every
interrupt restore and at every turn of a halt (`bw_os_cpu_step`), so a reply
the ARM9 waits for is produced. After N frames the run prints a summary and
the resident overlays and exits 0; a panic ends it with the panic's message,
the frame it reached, the resident overlays and the call chain
(`sdk/plat_crash.h`, which also reports a host crash and, with
`--watchdog`, a run that passes no frame for S seconds with every thread's
chain). `--screenshot` writes both screens as a PNG at the end of each
named frame, with or without a window.

The frames run on the game's idle thread, so the window belongs to it: it
is opened at the first frame, and pumped, drawn and closed there (a Win32
window created on `main` was never pumped while `main` sat in the game's
`OS_WaitIrq`). The sound driver is the game thread's too, so each frame
renders its share of output on that thread and queues it on the device
(the platform layer's push mode), rather than SDL's audio thread running
the driver.

`test_boot_run` (data-gated, `tests/boot_run.cmake`) runs it headless for
more frames than it gets through and passes when it stops at the build's
documented next stop at or past the furthest frame it is known to reach
(both set in `cmake/boot.cmake`); `test_boot_window` runs 300 frames with
`--window` through SDL's dummy drivers.

**How far it gets.** With the title overlays compiled in, to the title
menu. The system initialiser and the heaps; the boot sequence
(`func_0200523C`: the resident ov010 and ov011, the network library's set-up
in ov009 and ov013, the save layout with its 69 blocks, ov228's save-data
set-up); then the frame loop: the Nintendo and The Pokemon Company logos
(frame 30), the copyright screen (frame 240), the opening (ov179, from about
frame 600), and the title screen (ov088, "PRESS START", from about frame
4600). With no input the game loops back to the opening, as the cartridge
does; 20000 frames run without a stop. With `--press START@4800` (or the
key in a window) the title menu opens (NEW GAME, MYSTERY GIFT, NINTENDO WFC
SETTINGS, MIC TEST) and runs; `test_boot_run` asserts exactly that. What
lies past the menu (a new game's first scenes, the field) is the next
frontier.

`--press BUTTONS@FRAME[:HOLD]` and `--input SCRIPT` give the run timed
input (sdk/input.h's script), which joins a window's keys: `bw_input_frame`
runs at every frame, before its vblank.

**What the run needed**, each written where its kind of answer lives:

- Identity mapping ("Identity mapping" above), which made every pointer the
  game keeps in its data and every address it computes valid at once.
- The code pointers the metadata does not list, found by a scan of the data
  against every function the build defines (docs/armdata.md), and pointers
  from the ARM9 data into an overlay window relocated to the overlay's
  function.
- Every matched ARM9 game file in the boot (`EIDOS_BOOT_ALL_GAME`), so the
  functions reached only through tables exist.
- Arguments in registers (below), first stood in by `stubs/reimpl_` files
  and then named in aletheia's C.
- Functions aletheia had not found (the save block callbacks, the heap
  allocator's alloc and free, a G3D joint-scale function) and three
  unmatched overlay functions, each stood in by port C written from the
  listing until aletheia matched it.
- asm bodies in C (`sdk/asm/`): the matrix set-ups and copies of `fx_mtx`,
  the MI block copies, the DWC task allocator and a few one-line SDK
  accessors.
- A symbols row's address over a spelling defined elsewhere (`sub_0204968C`
  calls 0x020307B0 "ENV_SetResourceSet", the SDK's is 0x0206434C), linker
  veneers from the listing's `veneer_` labels, and a seed list that skips a
  file aletheia added before its manifest lists it (`tools/bootlink.py`,
  `tools/closure.py`, `tools/ovlink.py`).
- Earlier: the arena table and the DMA module (`sdk/os_arena.c`,
  `sdk/mi_dma.c`), `sdk/boot/`'s SDK statics, the ARM7's touch-panel
  responder, all of main RAM committed at start-up.

## Arguments in registers

mwcc compiles `f(); g();` with nothing between the two `bl` instructions,
so if `g` takes an argument it receives whatever `f` left in r0; and a
function that calls `g()` with fewer arguments than `g` takes hands on its
own incoming r1-r3 untouched. aletheia's C reproduces the bytes either way,
because the value is already in the register, but a host compiler passes
what the C says, so the callee reads an indeterminate value: a heap
allocation with a random alignment that failed in some runs and not others,
a save block getter reading NULL, an animation advanced by a garbage count.

`tools/regargs.py` lists every such site in the matched corpus (2306 when
the port first ran it, 74 at aletheia commit e06766e4): for each function
that calls a callee it declares with fewer parameters than the callee's
definition takes, where the callee uses the
missing one, it reads the caller's code in the listing and says where the
register comes from (the caller's own argument, the previous call's
result, or something to read by hand). aletheia names the arguments in its
C, byte-identical, from that list. Until it has, a site on the boot's path
is a `stubs/reimpl_` file (`stubs/ov/reimpl_ovNNN_` for an overlay, which
`tools/ovlink.py` compiles in the matched file's place) that names the
argument, and is deleted once aletheia's file does.

Tail-call thunks are the same problem in bulk: about 290 matched files are
`void f(void) { g(); }`, which on the DS is `ldr ip, =g; bx ip` and passes
every argument and the result through. `tools/bootlink.py` compiles a
generated forwarder in place of each one in the boot, with the callee's
normalised prototype (`<build>/boot/boot_thunks.txt` lists them).

## Modding is a design constraint, not a later feature

eidos is meant to carry new Pokemon, moves, sprites, NPCs, maps and AI.
Nothing here may freeze a DS limit the port owns:

- Game tables are host objects registered with `bw_ds_register`, not fixed
  DS memory, so a table can be defined larger than the cartridge's copy and
  the matched code that indexes it keeps working; the limit that remains is
  the one written into matched code (a count compared against a constant),
  and those sites are recorded as they are found, not worked around.
- Assets reach the game through the VFS and its mods (`sdk/vfs.c`), and a
  mod can replace or add single NARC members (`sdk/vfs_narc.c`), so it adds
  one sprite or one map without repacking an archive; an archive grows past
  its cartridge count up to the format's 65535.
- Where the port substitutes behaviour (a shim, an overlay registry entry, a
  hook point), it is a replaceable function or table, not hard-wired, so AI,
  scripts and procs can be swapped by a mod later.
