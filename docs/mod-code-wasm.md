# Code mods in WebAssembly: the agreed design

Status: agreed with kenon on 2026-10-21; the contract is mod API version 4
(`sdk/api/v4`). The loader is built (`sdk/mod_wasm.c`, "The loader" below):
a `.wasm` code mod loads and runs. Overrides, three service handlers and
the per-instance limits are still to come (docs/mod-backlog.md).

## Summary

- A code mod ships one portable file, `code = mod.wasm`, run by an
  embedded runtime. The same file works on every platform.
- Mods are written in C against generated headers and built by kenon
  (Zig) to `wasm32-freestanding`. No WASI: a mod reaches nothing outside
  the game except through imports.
- Native libraries (`.dll`, `.so`, `.dylib`) stay as a developer tier that
  the player must enable explicitly ("unsafe native mod"). Their main use
  is debugging.
- The sandbox protects the player's machine, not the run: a mod that
  writes game memory can still break the game, as a native mod can.

## Runtime

WAMR, fast interpreter, by default (Apache-2.0 with the LLVM exception;
CMake; Windows, Linux, macOS, Android, iOS). Only `.wasm` ships. An AOT
cache compiled on the player's machine may come later. wasm3 is not used
(in maintenance mode, interpreter only).

Measured by kenon (Rust mod, same code three ways): an empty hook call is
1.3 ns native, 24.5 ns compiled wasm and 47 ns interpreted; a full AI turn
is 1.7, 3.0 and 33 microseconds. A frame is 16,700 microseconds.

## Seams kept for a later Lua tier

The bridge is built so that a second scripting backend (Lua 5.4 or Luau)
can be added without changing the registry, the hook slots or the
manifest.

1. One language-neutral API description is the single source:
   `sdk/api/v<N>/` holds `events.json` (name, id, payload fields with C
   type, offset, writable, refusable), `services.json`, `hooks.json` (the
   declared set with each row's prototype and region), `settings.json`, and
   the struct accessor description. The C headers (`mod_api.h`,
   `mod_state.h`, the struct accessors, `eidos_wasm.h`) and the wasm import
   table are generated from it; a Lua binding would be generated from the
   same files. A check fails the build when the generated snapshot and the
   committed one differ without a version bump.
2. A runtime-neutral host layer. The event registry, services, hook slots,
   settings, logging and per-mod state talk to one internal "mod instance"
   interface: call a handler, call an export, read or write game memory,
   marshal a payload, and the per-instance limits. WAMR implements it; a Lua
   backend would be a second implementation of the same interface.
3. One manifest key. `code =` names the file and the kind is taken from the
   file: the wasm magic, a native library header, or for a text script its
   extension (`.lua`).
4. Values, never host pointers. Payloads, hook arguments and game memory
   cross the boundary as integers, DS addresses (u32) and byte copies. A
   game pointer is the object's DS address (exact in the identity-mapped
   32-bit reference build; `bw_ds_addr_of` for host objects, which also
   holds on a 64-bit build). Memory goes through bounds-checked imports
   (`rd8/16/32`, `wr8/16/32`, `copy`).
5. Limits per instance, owned by the interface: memory cap (default
   64 MiB, manifest `memory = <MiB>`), a step budget per call (WAMR's
   instruction metering; a Lua hook count for Lua), and re-entrancy depth
   (a mod calls a service that fires an event back into the same mod).
   Wasm execution is deterministic, which the co-op and net services rely
   on; a Lua backend must keep that (no `os`, `io` or unseeded randomness).

## The wasm module (api 4)

The contract is `sdk/api/v4`: `eidos_wasm.h` is the header a mod compiles
against, `core.json` lists the core imports and the exports, and
`events.json`, `state.json`, `services.json` and `enums.json` describe the
rest. All of it is generated by `tools/apigen.py` from the port's headers.

- Import module `"eidos"`. The core imports: `log(text, len)`;
  `on(kind, index)` binds an event handler; `script(vm, opcode, index)`
  binds a script command handler; `override(region, addr, index)` installs
  a hook on a function of `hooks.json`, and inside it
  `original(args, nargs)` calls the next link with the arguments as an array
  of u32 in the mod's memory; `rd8/16/32` and `wr8/16/32` read and write one
  value of game memory at a DS address; `read(addr, dst, len)` and
  `write(addr, src, len)` copy a block between game memory and the mod's
  memory (bounds-checked, non-zero when out of bounds).
- Every state call and service is an import of the same name. A Pokemon
  reference goes as its five fields, a pointer as an address in the mod's
  memory, a handler as a function table index.
- Exports: `eidos_mod_start() -> i32` (0 = ok), `eidos_mod_stop()`, the
  function table, and `memory`. The instance is the mod's state.
- A handler receives a copy of the payload in the mod's memory and returns
  `EIDOS_EVENT_CONTINUE` or `EIDOS_EVENT_REFUSE`; the port reads the
  writable fields back after it returns.
- Stack 64 KiB (template linker flag). The template brings a small
  allocator and the compiler-rt builtins (no libc).
- Threads: the port runs one game thread at a time (the run token), so a
  WAMR thread environment per host thread that calls in is enough.
- Callbacks the game stores (task callbacks, comparators) go through a
  bounded pool of host trampolines that dispatch to wasm exports.

## The loader

`sdk/mod_loader.c` reads the first four bytes of the `code =` file. The
wasm magic (`\0asm`) sends it to `sdk/mod_wasm.c`; anything else is opened
as a native library. Both kinds get the same host table, the same
namespace, settings and tables, and the same place in the load order.

- One WAMR runtime serves every mod. It is started at the first wasm mod
  and registers the imports of module `"eidos"`: the core imports by hand,
  and one native per state call and service generated by `tools/apigen.py`
  into `sdk/mod_wasm_natives.inc`. Every import must be one of these
  functions with its signature. A module that imports anything else (an
  unknown name, another signature, a memory, table or global) does not
  load, and the log names the import.
- Each mod is one instance with a 64 KiB stack. WAMR's own app heap is not
  used. Right after instantiation the port grows the module's memory by one
  page: that page is the port's, for payload copies. The pages the module
  declared and the pages it grows later with `memory.grow` stay its own, so
  an allocator that starts at `__heap_base` and grows with `memory.grow`
  never meets the port's page. A module must not treat memory past the
  size it declared as its own without growing it first. The module needs
  no allocator export, and its memory maximum (if it states one) must leave
  room for one more page.
- An event handler runs on a copy of the payload in the port's page. The
  copy comes back after the handler returns, and the event layer applies
  only the fields the event marks writable. A script command handler gets a
  copy of the command the same way. The page is used as a stack, so an
  event that fires inside a handler gets its own copy above the first.
- A pointer argument is checked against the module's memory for the whole
  object the port reads or writes there, not only its first byte.
- A trap (an `unreachable`, an out-of-bounds access, a bad table index) ends
  that call only. It is logged with WAMR's message, the event goes on as if
  the handler had answered `EIDOS_EVENT_CONTINUE`, and the mod stays loaded.
- `on_frame` uses a pool of 16 host trampolines, one per mod that binds a
  frame handler. A mod's slot is given back when the mod stops.
- `on_session` and `on_command` use pools of the same kind. A session
  handler is a table entry `(peer, kind, bytes, size)`; a command handler is
  `(text, length)`. The bytes and the text are copies in the port's page
  (the text ends in a NUL), made the way an event's payload is.
- The Mods page of the settings reloads a changed `.wasm` file the same way
  it reloads a native library: the instance is stopped and freed, and a new
  one is made from the file.

Not yet: `override` and `original` answer -1, and `on_save_received`
binds nothing (a save does not fit the port's page); each says so once in
the log. The memory cap and the step budget of "Seams" item 5 are not
enforced.

`tests/test_mod_wasm.c` loads a hand-assembled module through the loader:
its handlers refuse or let an event go on by the payload's contents, a trap
lets the event go on, a broken module is refused, and the module loads
again after a stop.

## API versions

Version 4 adds wasm. The port accepts a list of versions (3 and 4), so
native mods built for 3 keep loading.

## Order

Content limits first (items, then moves; docs/research/limits/), the
`.bw` reader (spec in kenon's docs/bw-format.md), then this bridge: events
and services first, overrides and memory access second. The struct
accessor generator lives in eidos `tools/`, reading aletheia's
self-contained headers at the pinned revision.

## kenon's side

The C template, the editor and the Zig build, manifest validation, the
message-bank encoder and NARC member writers, `.bw` packing, a debug runner
using eidos's `--mod <folder>` and `--mod-log <file>`, and one sample mod
per feature that both sides use as a conformance test.
