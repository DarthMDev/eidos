# Running the game on 64-bit-only hosts

`docs/pointer-width.md` made ILP32 the reference configuration: on a 32-bit
target the matched code's structs have the DS's own bytes, and the corpus is
full of assumptions that a pointer is four bytes. That rules out macOS and
iOS (no 32-bit processes at all) and, increasingly, Android (arm64-only
devices, 64-bit-only store requirements). Multi-platform is a hard
requirement, so this document decides how eidos runs the game on a host
where every process is 64-bit, with measurements taken on this machine
(Windows 11, MinGW-w64 GCC 14.2, MSVC 14.50, Visual Studio's clang 20.1.8).

**Decision: the game is never compiled LP64. Everywhere, it is compiled for
an ILP32 target: natively (i686, armv7) where the OS still runs 32-bit
processes, and for wasm32 elsewhere, translated back to portable C by
wasm2c and compiled by the platform's own C compiler.** wasm32 is the one
ILP32 target that exists on every platform, because after wasm2c it is not
a target at all: it is C, and the 32-bit address space is an array.

## What "ILP32" has to mean: the DS's struct layouts

The property the port needs is not "pointers are four bytes" but "every
struct the matched code declares has the layout the DS's compiler gave it".
`tools/lp64/layouts.py` measures that directly: for each matched unit of the
boot closure it asks clang for the layout of every record the unit's code
generation needed (size, alignment, every field offset, bit-field placement)
on each target, and compares it with `armv5te-none-eabi` (the DS ABI;
int-sized enums, as CodeWarrior's `-enum int` gives).

1004 matched units of the boot closure, 678 record layouts:

| target | records that differ from ARM | of which the size differs | units affected |
|---|---|---|---|
| wasm32 | **0** | 0 | 0 |
| i686 Windows (MinGW, the current ILP32 build) | **0** | 0 | 0 |
| i686 Linux | 12 (8 types) | 5 | 12 |
| i686 Linux with `-malign-double` | **0** | 0 | 0 |
| x86-64 Windows | 367 (171 types) | 367 | 284 |
| x86-64 Linux | 387 (190 types) | 387 | 294 |
| aarch64 Linux (and so Android, macOS, iOS) | 387 (190 types) | 387 | 294 |

Three findings:

1. **wasm32 lays out every one of them exactly as the DS does.** Its C ABI
   aligns a 64-bit integer and a double to 8, like the ARM EABI.
2. **"ILP32" on Linux is not quite the DS.** The i386 System V ABI aligns
   `long long` and `double` to 4 inside a struct, so `MATHRandContext64`,
   the heap layer's `GflHeaps`, `struct Lcg64` and five other records move.
   `-malign-double` restores the ARM alignment exactly (0 differences, the
   row above). `cmake/ilp32-toolchain.cmake`'s Linux fallback should pass
   it, for the matched sources at least (it changes the i386 ABI of a
   struct passed to the C library, which the matched code never does).
3. **The LP64 numbers are worse than pointers alone.** 1241 matched files
   (of 24889) spell a 32-bit type with `long` (`typedef unsigned long u32`,
   `typedef long fx32`, the SDK's own spelling). On every LP64 target except
   Windows that makes `u32` eight bytes and changes fixed-point overflow, not
   just layout. That is why x86-64 Linux and aarch64 differ in more records
   than x86-64 Windows.

## Option (a): a 32-bit address window inside a 64-bit process

The idea: compile the game LP64 but keep every address the game can see
(code, globals, heaps, thread stacks, the DS memory blocks) below 4 GiB, so
a host pointer still fits the DS's `u32`.

`tools/lp64/lowmem_probe.c` prints where a 64-bit process puts each of
those, and whether it fits a `u32`:

| build | code | globals | malloc 64 MiB | VirtualAlloc 128 MiB | thread stack | kernel32 / ucrtbase | all below 4 GiB |
|---|---|---|---|---|---|---|---|
| MinGW x64, default | 0x7FF7... | 0x7FF7... | 0x1A5... | 0x1A5... | 0x39... | 0x7FF8... | no |
| MinGW x64, LAA bit cleared, image base 0x10000000 | 0x0F81... | 0x0F81... | 0x01AD... | 0x05AE... | 0x0DCD... | 0x0101... / 0x0186... | **yes** |
| MSVC x64, default | 0x7FF7... | 0x7FF7... | 0x1EF... | 0x1EF... | 0xEB... | 0x7FF8... | no |
| MSVC x64, `/LARGEADDRESSAWARE:NO` | 0x004E... | 0x0050... | 0x00E4... | 0x04E5... | 0x0D09... | 0x007F... / 0x0CF3... | **yes** |

So on Windows a 64-bit process can be confined below 2 GiB, system DLLs
included. (This MinGW's `ld` rejects `--disable-large-address-aware` for
PE32+; clearing the flag in the header after the link does the same thing.)
Elsewhere:

- **Linux x86-64**: `MAP_32BIT` exists for data, a non-PIE executable keeps
  code low, but shared libraries load high. Moot anyway: Linux runs i686
  natively.
- **Android arm64**: no `MAP_32BIT`; `mmap` hints below 4 GiB are usually
  honoured for data, but the app is a PIE shared object loaded by zygote at
  a high address, so every function pointer the game stores is above 4 GiB.
- **macOS**: a normal arm64 executable has a 4 GiB `__PAGEZERO`, so nothing
  can be mapped below 4 GiB. `-pagezero_size` exists in the linker; whether
  current arm64 kernels accept a smaller zero page could not be checked
  without a Mac, and XNU's loader is documented to enforce a hard
  page-zero for 64-bit arm64 processes. Check on any Apple Silicon Mac with
  `cc tools/lp64/lowmem_probe.c -Wl,-pagezero_size,0x1000 && ./a.out`.
- **iOS**: no control over `__PAGEZERO` or the load address at all.

**And it would not be enough where it works.** The window makes a host
pointer *fit* in a `u32`; it does nothing for the layout. The game would
still be compiled LP64, so every struct with a pointer member is wider than
the DS's (the 367-387 rows above), every `u8 pad[0x14]` lands on the wrong
field, and the `long`-spelled `u32` is eight bytes on every non-Windows
host. A true ILP32 code model inside a 64-bit process exists only as
platform ABIs eidos cannot use: x32 (Linux x86-64, rarely enabled by
distributions) and arm64_32 (watchOS only). The one platform where the
window works, Windows, also runs real 32-bit processes. **Rejected.**

## Option (b): DS-sized pointers everywhere

The general form: compile the game so that a pointer *is* a 32-bit offset
into one block of host memory, and every dereference adds the block's base.
Then every layout, every `u32` holding a pointer, every pointer word in the
ARM9 data and every function pointer stored in a struct are exactly as on
the DS, on any host.

**As a custom compiler transformation** (a clang plugin or LLVM pass that
rewrites pointer types to `i32` offsets): this is the wasm32 code model
re-implemented by hand. LLVM's only 32-bit-pointer address spaces in a
64-bit target are x86's `__ptr32` (MSVC extension, x86 only, still needs
the memory below 4 GiB); there is nothing for AArch64. Writing and
maintaining a pointer-compressing pass for every backend is a project on the
scale of the port itself. **Dominated by the next variant.**

**As wasm32 + wasm2c**: compile the C with clang for `wasm32` (ILP32,
ARM-compatible alignment, a 32-bit linear memory), link with `wasm-ld`, and
translate the module back into C with wabt's `wasm2c`. The output is plain
C99 that any compiler builds for any target (MSVC, Xcode's clang for iOS and
macOS, the NDK), with the linear memory as a host allocation and each load
and store an offset from its base. No JIT, so iOS is fine. The port's shims
compile into the same module; what the host must answer is the module's
imports.

Measured, on the boot closure (`EIDOS_BOOT=ON`, configured ILP32, 1266
translation units from `compile_commands.json`, tests excluded) with
`tools/lp64/recompile.py`:

| | units |
|---|---|
| compiled by GCC i686 in the reference build | 1090 |
| compiled by clang for i686 (the control) | 1117 |
| **compiled by clang for wasm32** | **1109** |
| fail only for wasm32 | 8: 7 engine/audio files (`-msse2`, a host flag), `sdk/os_thread.c` (`setjmp`) |
| fail for both clang targets | 149: 70 generated `tools/dsaddr.py` copies the incomplete boot build had not produced, 56 asm-bodied matched files, 23 calls to undeclared functions |

Every unit that compiles for native ILP32 compiles for wasm32, except for
two port files whose answer is known (below).

### The one real incompatibility: disagreeing prototypes

aletheia's matched files declare each extern with the prototype their call
site needed, so the same function is often declared differently in
different files (`docs/pointer-width.md`, signal A2). On the DS and on i686
that is harmless. A wasm call is type-checked: `wasm-ld` replaces a direct
call whose wasm signature differs from the definition's with a stub that
traps, and warns. A pointer against an integer is *not* such a difference
(both are `i32`), which removes most of A2; what remains is a different
parameter count, or a value return against `void`.

- **Boot closure** (1031 objects after the 77 duplicate definitions the
  unmerged boot link still has were dropped): **62 functions**, 32 differing
  only in the return, 25 only in the parameter count, 7 in both. One more is
  an error rather than a warning: two callers disagree about a function no
  object defines yet.
- **The whole corpus**, statically (`tools/lp64/wasm_sigs.py`, the same
  prototype parser as `--pointer-audit`): 5912 of 29128 declared game
  functions. This parser over-counts: over the boot closure it reports 221
  where the link reports 62, so the corpus figure is an upper bound, probably
  around 1700.

**The fix is mechanical and lives in the build.** `tools/lp64/sigfix.py`
reads wasm-ld's warnings, finds which side defines the function, and for
each disagreeing caller adds `-D<func>=<func>__as_<sig>` to that caller's
compile (the same kind of flag as the existing `-Dg_02146B64=sRootList`)
plus a generated adapter with the caller's signature that calls the
definition with the definition's: extra arguments dropped, missing ones 0, a
missing return value 0. Link, fix, relink until clean. On the bench (the
eidos library, 152 units) it converges in 4 passes to 16 adapters, and the
module then validates and runs with checksums identical to native i686.
No matched file is edited.

Two dead ends, recorded so nobody repeats them:

- **LTO instead of adapters.** With `-flto`, LLVM's
  `WebAssemblyFixFunctionBitcasts` pass writes the wrappers itself and the
  link reports nothing. But it compares IR types, where `u16` and `u32` are
  different, so a `u16` parameter declared `u32` elsewhere gets a wrapper
  that traps (`_bitcast_invalid`): 71 such targets in the boot closure,
  `sub_02030734` (the allocator) and `MI_CpuFill8` among them. Worse than
  no LTO.
- **Archives.** wasm-ld 20.1.8 skips the signature check when the call is
  resolved by fetching an archive member and writes an *invalid* module
  (a call with the wrong number of operands) instead of a trap stub, with no
  warning. Reproduced with two files. Link objects, not archives, and always
  run `wasm-validate` (both done in `tools/lp64/bench/build.py`).

Calls through function pointers are checked at run time instead
(`call_indirect`). A pointer stored with one prototype and called through
another traps when called. This cannot be counted statically; the safety
net is binaryen's `--fpcast-emu` (every indirect call through one
signature), measured below.

### Size and build time

The boot closure (LTO link, every function exported so nothing is
stripped): 2412 functions, 1.3 MB of wasm. `wasm2c` turns it into 12.4 MB
of C (299,706 lines) in 3.6 s. MinGW GCC x64 `-O2` compiles that in 58 s
to 1.27 MB of code; MSVC x64 `/O2` in 13 s. The generated C is warning-free
at the compilers' default levels; at `-Wall -Wextra` it has thousands of
unused-value and unused-parameter warnings, so the generated file gets
warnings off by itself (one documented exception to the warning-free rule,
for code no person writes). The bench module also compiles for
`aarch64-w64-windows-gnu`, a 64-bit-only ARM target.

### Performance, on the game's own code

The engine tests are port code and the boot does not link yet, so
`tools/lp64/bench/bench.c` drives three pieces of matched game code the
library already carries at ILP32: the game's expanded heap and its manager
(2M random allocations and frees: pointer chasing over free lists), the
game's task-callback scheduler (200k frames of 48 tasks: a priority list
walk and an indirect call per task), and the SDK's `MTX_Concat43` (5M
fixed-point 4x3 products with 64-bit intermediates). Same sources, `-O2`
everywhere, median of 7 runs, relative to native i686 (lower is faster).
Every run's three checksums match the native ones.

| configuration | heap | tcbl | mtx |
|---|---|---|---|
| native i686 GCC (the reference) | 1.00 (291 ms) | 1.00 (48 ms) | 1.00 (286 ms) |
| wasm2c, x64 MinGW GCC, wasm2c defaults | 2.19 | 6.88 | 0.75 |
| wasm2c, x64 MSVC, wasm2c defaults | 1.72 | 2.10 | 1.09 |
| wasm2c, x64 MinGW GCC, guard pages, no stack-depth count | 0.95 | 1.34 | 0.86 |
| wasm2c, x64 MSVC, guard pages, no stack-depth count | 1.00 | 1.24 | 0.68 |
| wasm2c, x64 MinGW GCC, explicit bounds checks, no stack-depth count | 1.80 | 2.05 | 1.17 |
| wasm2c, x64 MSVC, explicit bounds checks, no stack-depth count | 1.97 | 2.45 | 1.18 |
| **wasm-opt -O2, then wasm2c, x64 MinGW GCC, guard pages** | **0.75** | **1.11** | **0.64** |
| wasm-opt -O2, then wasm2c, x64 MSVC, guard pages | 0.97 | 1.20 | 0.74 |
| wasm-opt -O2 `--fpcast-emu`, wasm2c, x64 MinGW GCC, guard pages | 0.71 | 1.72 | 0.60 |
| wasm-opt -O2 `--fpcast-emu`, wasm2c, x64 MSVC, guard pages | 1.16 | 1.69 | 0.68 |

What the rows mean:

- **Guard pages** reserve the 4 GiB linear memory plus guards and let the
  MMU catch an out-of-range offset, so the code has no bounds checks; this
  is the normal mode on a 64-bit host. **Explicit bounds checks** are for a
  host that cannot reserve that much address space; they cost about 2x on
  this workload.
- **The stack-depth count** is how wasm2c traps on runaway recursion where
  it has no signal handler, which includes every Windows build; it is the
  whole of the 2-7x in the default rows. A native build does not check
  stack depth either, so turning it off
  (`WASM_RT_NONCONFORMING_UNCHECKED_STACK_EXHAUSTION`) costs nothing the
  native port had.
- **`--fpcast-emu`** costs about 50% on the indirect-call-heavy scheduler
  and nothing elsewhere. It is the fallback if run-time `call_indirect`
  mismatches turn out to be common, not the default.

With guard pages and binaryen's optimiser, the game's code runs as fast as
native i686 or faster (x64 has more registers and native 64-bit multiplies,
which is the whole difference in the matrix column). For scale: the DS's
ARM9 runs at 67 MHz, and a frame of the game is a few hundred thousand of
these operations at most. Even the slowest row is not a constraint.

  A1  3936

  B2  1308
  B3  489

```

plus 1241 files whose `u32`/`fx32` are `long`. When `docs/pointer-width.md`
was written the corpus was 1110 files and 57.8% of them were affected. At
aletheia revision e06766e42c the corpus is 33541 files and 42.6% are
affected. The fraction fell, against both earlier readings. The absolute
count did not: 14301 files are affected now against 642 then, and the B1
count rose from 355 to 4766 even as the affected share shrank. This document
and `docs/pointer-width.md` recorded different audited counts for the same
command (24904 against 1110), and this section's own earlier measurement
(24904 files, 18345 affected, 73.7%, B1 4130) agrees with the fresh run only
on B1's direction: the share fell from 73.7% to 42.6% and affected files fell
from 18345 to 14301, while B1 rose from 4130 to 4766. Each fix is an edit to
an EXACT matched file and needs a DS re-verify in the same aletheia commit
(README.md, portability rule 1), and the B1 half is not a fix at all but
missing knowledge (`u8 pad[0x14]` stands for fields nobody has identified).
The exit condition `pointer-width.md` set (B1 small enough to re-verify) is
stated in absolute files, and on that count it is further away, not closer.
The affected share moved the other way, so the direction is left as an open
question here rather than settled. At 14301 affected files the route still
does not scale, and with (b) it is not needed. **Rejected as a route to
LP64.** Declaring pointer fields as pointers remains good practice for
aletheia, but nothing in eidos waits on it.

## Recommendation

1. **One compilation model for the game, ILP32, on every platform.** The
   matched code, the port's shims, the data layer and the engine are
   compiled for an ILP32 target and nothing else. LP64 builds of the game
   stop being a goal. (The LP64 configuration keeps building as today until
   the wasm32 configuration replaces it as the 64-bit answer; see the plan.)
2. **Native ILP32 for development**: i686 on Windows (exact layouts,
   measured) and on Linux (with `-malign-double`), the fastest edit-build-
   debug loop with a native debugger on the matched source.
3. **wasm32 + wasm2c for 64-bit-only hosts**: macOS, iOS, arm64 Android,
   Windows on ARM, and optionally x64 Windows and Linux shipping builds.
   Built with guard pages, without the stack-depth count, after `wasm-opt
   -O2`, with sigfix adapters.

The costs:

- **A toolchain dependency for that configuration**: a clang with the
  wasm32 target and `wasm-ld` (Visual Studio's bundled LLVM has both; so
  does any LLVM release and wasi-sdk), wabt's `wasm2c`, binaryen's
  `wasm-opt`, and a libc for wasm (wasi-libc's sysroot; pair it with the
  clang's LLVM version: wasi-sdk 34's needs a newer `wasm-ld` than 20.1.8,
  wasi-sdk 25's works). Steps 1 and 2 of that build are
  platform-independent, so a mobile build only needs the platform's own C
  compiler for step 3.
- **Debugging** in that configuration is debugging generated C. That is why
  native ILP32 stays the development configuration: a bug reproduces there
  first, or it is a wasm2c-configuration bug and the differential test below
  finds it.
- **Indirect-call type checks** can trap where the DS would not. Unknown
  count; mitigations measured (`--fpcast-emu`, or a per-site adapter once
  the trap reports which call).
- **Two port files** need a wasm path (threads, below).

What it buys: exact DS layouts on every platform, zero edits to aletheia,
the data layer's pointer relocation works unchanged (`bw_data_relocation_
supported()` is true: pointers are four bytes), the nine tcbl files and the
matched heap come back on every platform, and performance at parity with
native.

## The wasm32 configuration's architecture

**What is inside the module**: everything the port compiles today except
the platform layer: the matched game code, `sdk/` (dsmem, the OS layer, PXI
and the ARM7 stand-in, fs/overlays/VFS, armdata), the engine (2D, 3D,
audio). All of it is already ILP32-clean, because the i686 configuration
exists. **What is outside**, as imports answered by native code: file access
(the VFS's reads), host threads and the run-token lock
(`sdk/plat_thread.c`'s API), the clock, and the SDL window, input and audio
output. The native renderer and mixer read their buffers straight out of
linear memory (a base pointer plus the offset the module passes); moving a
hot engine path native later is the same mechanism.

**Threads.** The OS layer already runs exactly one game thread at a time
under a run token, and that is what makes one wasm2c instance enough: each
`OSThread` is still a host thread, all of them execute the same instance,
and only the token holder ever does. The two per-thread pieces of wasm state
are swapped by the native side of the token handoff: the shadow-stack
pointer (`__stack_pointer`, exported from the module; each thread's shadow
stack is the stack memory the game passed to `OS_CreateThread`, which is in
linear memory) and wasm2c's own thread-local runtime state
(`wasm_rt_init_thread` per host thread). Linear memory needs no atomics:
the token's mutex is a full barrier and every handoff is an opaque import
call. `sdk/os_thread.c`'s `setjmp`/`longjmp` (a terminated thread unwinding
to its trampoline) becomes, under `__wasm__`, a call to a host import that
`longjmp`s on the native side to the host thread's own trampoline; the frames
it unwinds are wasm2c's generated C, which is what wasm2c's own traps already
do. `sdk/plat_thread.c` is the import's native implementation.

**Memory.** The simplest correct layout is today's: `sdk/dsmem.c` allocates
its regions inside linear memory like any other C object. A later
optimisation becomes possible only here: link with `--global-base` above
`0x08000000` and place the DS regions at their own addresses in linear
memory, so a DS address *is* a wasm pointer. `bw_ds_ptr` for main RAM, WRAM,
palette and OAM becomes the identity, the pointer words in the ARM9 data
need no relocation (only code words, which become table indices), and most
of `tools/dsaddr.py`'s rewrites become no-ops. VRAM banking and the I/O
access hooks keep their translation. No change to `sdk/dsmem.h` is needed for
either layout.

**Data and overlays**: unchanged. The image comes from the player's
`arm9_dec.bin` at reset as today; overlay code is linked into the module like
it is linked into the native executable.

## Migration plan

Each step has an exit condition; none changes the default build.

1. **Prototypes and measurements** (`tools/lp64/`, this document).
2. **The configuration**: `cmake/wasm32-toolchain.cmake` (clang
   `--target=wasm32-wasip1`, the sysroot) and an `EIDOS_WASM2C=ON` super-build
   (`cmake/wasm2c.cmake`): stage 1 builds the module with the existing source
   lists and runs the sigfix loop as a build step (per-source defines and the
   adapter file in the build tree, never in the repo), `wasm-opt -O2`,
   `wasm-validate`, `wasm2c`; stage 2 compiles the generated C, the wasm2c
   runtime and the host layer with the host compiler. Each test is a WASI
   command module run by the same host. A `tools/fetch_wasm.py` in the style
   of `fetch_sdl.py` pins and hash-checks wabt, binaryen and the wasi-libc
   sysroot into `third_party/`. Exit: every test that passes at ILP32 passes
   under wasm2c on Windows x64 with MinGW and MSVC, and `tools/check.py`
   gains `wasm2c-mingw64` and `wasm2c-msvc64`.
3. **The host layer**: the thread and token imports, the shadow-stack swap,
   the `__wasm__` thread-exit path in `sdk/os_thread.c`, file access through
   the VFS's imports instead of WASI preopens, SDL outside the module. Exit:
   `test_os_thread`, `test_armdata_real` and `eidos_view` run under wasm2c.
4. **Differential boot**: once the boot runs natively, run it in both
   configurations and compare a hash of DS memory and the register file after
   every frame. The two must be bit-identical; the first frame that
   differs names the bug. This is also the detector for `call_indirect`
   traps.
5. **64-bit-only platforms**: build the stage-2 C on macOS arm64 and Linux
   arm64 in CI, then iOS and Android packaging (Milestone 9). Decide guard
   pages versus bounds checks per platform by whether an 8 GiB reservation
   succeeds (iOS without the extended-virtual-addressing entitlement may
   refuse it).
6. **Retire LP64 game builds**: when step 2's exit condition holds, the
   `stubs/reimpl_` LP64 stand-ins and `EIDOS_TCBL_HEADER_BIAS` are no longer
   needed for any shipping target; README.md "Pointer width" and
   `docs/pointer-width.md` are updated to point here. The port's own code
   stays LP64-clean (portability rules 2 and 5 still apply to it), because the
   native host layer is LP64.

## Reproducing every number

Tools fetched for the measurements, all outside the repository: wabt 1.0.42
(`wasm2c`, `wasm-validate`, `wasm-objdump`), wasi-sysroot 25.0 and its
`libclang_rt.builtins-wasm32`, binaryen version_133 (`wasm-opt`), from the
projects' GitHub releases. The clang, `wasm-ld`, `llvm-ar` and `llvm-nm` are
Visual Studio's (`VC/Tools/Llvm/x64/bin`, LLVM 20.1.8).

```
# an ILP32 boot build with a compilation database (it need not link)
cmake -S . -B <b32boot> -G Ninja -DALETHEIA_ROOT=<aletheia> \
    -DCMAKE_TOOLCHAIN_FILE=cmake/ilp32-toolchain.cmake -DEIDOS_BOOT=ON \
    -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
cmake --build <b32boot> -- -k 0

python tools/lp64/layouts.py --build <b32boot> --clang <clang> --aletheia-root <aletheia>

The boot-closure link figures come from linking `recompile.py`'s wasm objects
with `wasm-ld --no-entry --no-gc-sections --allow-undefined --export-all`
(first-definition-wins for the duplicates) and counting the "function
signature mismatch" warnings; `--allow-undefined` is needed because the boot
link on main is not complete yet.

Timings were taken while other builds were using the machine; the
relative numbers were stable across three full runs to within about 15%, the
absolute ones were not.
