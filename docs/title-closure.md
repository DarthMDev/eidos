The boot starts one proc with a constant argument: `global CallProc(-1, 0x020A0480)` at 0x02005270, the **root
proc**, ARM9 code: init 0x0202F9F4, main 0x0202F9F8, end 0x0202FAB0. Its main (`func_0202F9F8`) is a
five-state machine that starts, in order:

1. ov088 proc data 0x021BD8E8 (save_control_intr.c, startmenu.c)
2. ov179 proc data 0x021B68D8 (cdemo_main.c)
3. ov088 proc data 0x021BD574 (save_control_intr.c, startmenu.c)

State 0 starts the first proc. States 1, 2 and 3 start the cdemo proc with a mode
of 0, 1 and 2 in its shared work area (`g_02146948`, mode at +0, skip byte at +3).
The cdemo main (`func_021B6380`) sets the skip byte when A, B or Start is pressed
(key mask 0xB). State 2 tests it after mode 0: set, the machine goes to state 4;
clear, modes 1 and 2 run (state 3 does not test it). State 4 starts the second
ov088 proc and the machine returns to state 0 when that proc ends. By the source
file names: a save-data check (`save_control_intr.c`, ov088), the opening cinematic
as up to three cdemo segments (`cdemo_main.c`, ov179), then the title menu
(`startmenu.c`, ov088). The procs the title menu starts are the exits listed under
its screen; they lead past the title menu and are not followed.

## How to read this

A screen is a proc: the closure of its init, main and end, plus the static
initialisers of overlays it loads. The script decodes the code itself (Thumb and
ARM, including mwcc's switch jump tables, which aletheia's listings leave as data
words), so it sees calls the listings do not. A function is reached as

- **static**: every edge on its best path is a direct BL/BLX/B, or a call or tail call
  through a register the backward scan resolves to a constant (this includes a load
  through a constant pointer and a callee that always returns the same pointer, as
  in the boot's net-table call);
- **pointer**: the best path needs a code pointer that a function loads from its own
  literal pool or builds with `adr` (a callback it registers, a task, a sequence
  function), or an entry of a constant function table that the function calls
  through with an index (`ldr rN, [table, idx]; blx rN`, the shape of cdemo's state
  machine; the table is the run of consecutive code pointers at its address).
  Resolved, and nearly always run, but through a pointer;
- **table**: the best path needs a code pointer found in a data object whose address
  a function loads (state tables, vtables, command tables). The object is bounded by
  the next address anything in the region points at, at most 0x200 bytes, so this
  tier over-approximates: it is the right list for "what could this screen run",
  not for "what does it run";
- **unlabelled**: reached by pointer but with no label in aletheia's listing (code
  disasm.py never traced, so it has no manifest entry by construction).

**Open** sites are register calls the scan cannot resolve (struct fields, vtables,
callbacks handed in by a caller). What they reach is not listed, so the totals are a
floor for static and pointer code. ARM9 callees are leaves of a screen (ARM9 is
fully matched); the boot walk does descend through ARM9.
