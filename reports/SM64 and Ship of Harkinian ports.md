# Mature ports rebuild the console, never emulate it

Not one mature decompilation-based or statically recompiled console port emulates the console address space or a memory-mapped register file. The Super Mario 64 port family, Ship of Harkinian (SoH) through libultraship (LUS), and N64Recomp all do the same things: they neutralize console addresses into host pointers, they replace the console SDK with a host library so the game's own calls keep compiling and running, and they reimplement hardware at the API level, not the register level. The one artifact they do interpret is the graphics command stream, and even that is a per-opcode interpreter over words the game generates at runtime, not a cycle model of the GPU ([sm64ex `gfx_pc.c`](https://github.com/sm64pc/sm64ex/blob/master/src/pc/gfx/gfx_pc.c); [LUS `interpreter.cpp`](https://github.com/HarbourMasters/libultraship/blob/main/src/fast/interpreter.cpp)). This inverts the intuition behind "emulate the DS": for a native Pokemon Black port, the console address space, the SDK, and save-file byte compatibility are optional or replaceable layers, while the genuinely necessary console machinery is smaller and more specific. Two findings change decisions hardest. First, the Nintendo DS reads hardware registers back, so a readable register file is the one artifact no N64 port ever had to build. Second, the widespread belief that sm64 reached 64-bit because its structs are fully declared with no explicit padding is contradicted by primary sources.

## No mature port emulates the address space, and the SDK becomes the host library

The N64 has a 32-bit virtual address space with KSEG0 at `0x80000000` mapping RDRAM and device registers under physical ranges like `0xA4xxxxxx` ([N64brew Wiki, Memory map](https://n64brew.dev/wiki/Memory_map)). Both port families define these constants and then compile the translation out. In the LUS ecosystem, `PHYSICAL_TO_VIRTUAL(addr)` becomes the identity while the real mapping sits commented out ([2ship2harkinian `mm/include/macros.h`](https://github.com/HarbourMasters/2ship2harkinian/blob/045edd624f93a7d1e793312514d2a4c6a77dc3cb/mm/include/macros.h)). sm64 does the same through `-DNO_SEGMENTED_MEMORY`: `VIRTUAL_TO_PHYSICAL`/`PHYSICAL_TO_VIRTUAL` and the 32-entry segment resolver collapse to plain casts, and `osVirtualToPhysical` is a straight identity ([sm64-port `include/macros.h`](https://github.com/sm64-port/sm64-port/blob/master/include/macros.h); [sm64-port `Makefile`](https://github.com/sm64-port/sm64-port/blob/master/Makefile); [sm64-port `src/pc/ultra_reimplementation.c`](https://github.com/sm64-port/sm64-port/blob/master/src/pc/ultra_reimplementation.c)). Display-list pointers are resolved by a bare cast, `seg_addr(uintptr_t w1) { return (void *) w1; }`, not a translation call ([sm64-port `src/pc/gfx/gfx_pc.c`](https://github.com/sm64-port/sm64-port/blob/master/src/pc/gfx/gfx_pc.c)). None of this leaves a per-address translation helper. There is no architectural counterpart to a `bw_ds_ptr`, and no codegen that enumerates console-address cast sites; the ports avoid preserving console addresses rather than mapping them ([sm64-port `src/game/memory.c`](https://github.com/sm64-port/sm64-port/blob/master/src/game/memory.c)).

Static recompilation reaches the same place from the other direction. N64Recomp translates MIPS machine code to literal C ahead of time, emitting one C function per input function with registers in a context struct, and the runtime keeps RDRAM as a flat host buffer addressed by a base pointer ([N64Recomp README](https://github.com/N64Recomp/N64Recomp)). The author explains why address-space emulation was skipped: N64 games "were also built with a system library which is used by game code to control the hardware," so "game code generally tends not to interact directly with memory-mapped registers since the system library handled that" ([Mr-Wiseguy, N64Recomp issue #26](https://github.com/Mr-Wiseguy/N64Recomp/issues/26)). Hardware access is therefore factored into a reimplemented libultra layer (`ultramodern`), not a register file ([N64ModernRuntime README](https://github.com/N64Recomp/N64ModernRuntime)). The flat-RDRAM and pointer-arithmetic details are corroborated only by machine-generated DeepWiki summaries, which are secondary; treat the exact allocation strategy as unverified ([DeepWiki: drmario64_recomp_plus](https://deepwiki.com/theboy181/drmario64_recomp_plus/9.2-n64modernruntime-(ultramodern-and-librecomp))).

The SDK is the artifact that actually gets rebuilt, and it is rebuilt as a header-compatible library. LUS states that it "is not a recompilation tool" but instead lets developers "build a game's original source code (derived from decompilation) on modern hardware by providing a header-compatible wrapper around modern reimplementations of N64 SDK functions," and that "in essence, LUS acts as 'compile-time WINE' for the N64" ([libultraship Porting Guide](https://libultraship.com/PORTING)). The porting workflow is literally a header swap plus stubbing: replace `#include <ultra64.h>` with `#include <libultraship/libultraship.h>`, then "Comment out or stub functions that LUS handles automatically (e.g., `osCreateThread`)" ([libultraship Porting Guide](https://libultraship.com/PORTING)). Many hardware-facing functions are outright no-ops. In LUS `os_vi.cpp`, `osViSwapBuffer`, `osViSetMode`, `osViBlack`, `osViSetXScale`, and `osViSetYScale` have empty bodies, and `osViGetNextFramebuffer`/`osViGetCurrentFramebuffer` return `nullptr`; presentation belongs to the window layer ([LUS `src/libultraship/libultra/os_vi.cpp`](https://github.com/HarbourMasters/libultraship/blob/main/src/libultraship/libultra/os_vi.cpp)). sm64's shim is the same shape in one file, with `osViSetMode`, `osViBlack`, and the cache writeback/invalidate functions marked `UNUSED` and effectively no-ops ([sm64ex `src/pc/ultra_reimplementation.c`](https://github.com/sm64pc/sm64ex/blob/nightly/src/pc/ultra_reimplementation.c)).

This places the techniques on a clear spectrum, from most emulatory to most native: interpreter emulator, then dynamic recompiler or JIT (still emulation), then static recompilation with no runtime decoding of translated code, then decompilation ports that never execute console machine code at all ([SED1735 transcript](https://softwareengineeringdaily.com/wp-content/uploads/2024/09/SED1735-N64-Recomp.txt); [libultraship Porting Guide](https://libultraship.com/PORTING)). Digital Foundry frames recompilation as "not emulating the behaviour of the hardware… nor is it going as far as decompilation" ([Nintendo Life, 2024-05-26](https://www.nintendolife.com/news/2024/05/video-digital-foundry-takes-a-look-at-zelda-64-recompiled-majoras-mask)). The decision implication is direct: emulating the DS address space and MMIO registers is not something the mature ecosystems do, and a claim that a decompilation port "emulates the console" is weak, because no console machine code runs at runtime.

## Graphics is the one artifact every port still interprets

A display list is an array of fixed 8-byte command words handed to the RSP, and the GBI is the macro interface the game uses to build it ([HackMD, "N64 Gfx Decompilation"](https://hackmd.io/@Roman971/Hk01jRxRr)). Both families execute that command stream directly. sm64ex's `gfx_run`/`gfx_run_dl` loops on `opcode = cmd->words.w0 >> 24` and switches across `G_MTX`, `G_VTX`, `G_TRI1`, `G_SETCOMBINE`, and the rest ([sm64ex `gfx_pc.c`](https://github.com/sm64pc/sm64ex/blob/master/src/pc/gfx/gfx_pc.c)). LUS's `Interpreter::Run` dispatches through `gfx_step`, checking the custom-command table first, then the microcode and RDP tables, and it supports six microcode profiles (`f3d, f3db, f3dex, f3dexb, f3dex2, s2dex`, default `f3dex2`) with a runtime switch on `G_LOAD_UCODE` ([LUS `src/fast/interpreter.cpp`](https://github.com/HarbourMasters/libultraship/blob/main/src/fast/interpreter.cpp)). Both descend from Emill's `n64-fast3d-engine` ([Emill/n64-fast3d-engine](https://github.com/Emill/n64-fast3d-engine)).

The critical property is that the game's own display-list-building C runs unchanged, because the port supplies drop-in `gbi.h` macros that write the same structures ([LUS `include/libultraship/libultra/gbi.h`](https://github.com/HarbourMasters/libultraship/blob/main/include/libultraship/libultra/gbi.h)). Dynamic, runtime-generated lists (animation matrices, per-frame geometry, code that builds `gDP*`/`gSP*` calls from `temp->unk0`/`unk4` writes) therefore execute by construction ([HackMD, dynamic commands](https://hackmd.io/@Roman971/Hk01jRxRr)). This is the strongest argument for interpreting the stream over a "reimplement the draw call" design: a high-level reimplementation would have to reproduce the DS 2D/3D engine behavior for every caller and would break on dynamically computed values, while the interpreter defers all of it to one engine that consumes the same words the hardware would.

There is no memory-mapped register file behind any of this. The graphics "registers" a game touches are not MMIO: the `gSP*`/`gDP*` macros write into an ordinary RAM `Gfx` buffer, and the microcode consumes it. What the interpreters keep instead are two behavioural state structs, `RSP` and `RDP` (matrix stacks, lights, geometry mode, combine mode, tile descriptors, viewport, scissor, framebuffer addresses), updated by the command handlers ([LUS `include/fast/interpreter.h`](https://github.com/HarbourMasters/libultraship/blob/main/include/fast/interpreter.h); [sm64ex `gfx_pc.c`](https://github.com/sm64pc/sm64ex/blob/master/src/pc/gfx/gfx_pc.c)). A `RenderingState` shadow diffs that state so GPU calls are only issued on change ([LUS `interpreter.h`](https://github.com/HarbourMasters/libultraship/blob/main/include/fast/interpreter.h)). Resolution is decoupled from the game's 320x240 assumption: N64 coordinates are interpreted natively and then scaled into the real window, with an X aspect correction for widescreen and dedicated "wide" commands for 2D HUD rects ([LUS `interpreter.h`](https://github.com/HarbourMasters/libultraship/blob/main/include/fast/interpreter.h); [sm64ex `gfx_pc.c`](https://github.com/sm64pc/sm64ex/blob/master/src/pc/gfx/gfx_pc.c)). Texture formats are decoded CPU-side into RGBA and uploaded ([sm64ex `gfx_pc.c`](https://github.com/sm64pc/sm64ex/blob/master/src/pc/gfx/gfx_pc.c); [LUS `interpreter.cpp`](https://github.com/HarbourMasters/libultraship/blob/main/src/fast/interpreter.cpp)), and LUS models framebuffers as first-class GPU objects with a `RegisterFbTexture` path that gives "full GPU resolution with no readback" ([LUS `interpreter.h`](https://github.com/HarbourMasters/libultraship/blob/main/include/fast/interpreter.h)).

Two caveats matter for architecture. First, the decomp is not pristine here: LUS injects a large block of custom opcodes (`OTR_G_SETTIMG_OTR_HASH`, `OTR_G_DL_OTR_FILEPATH`, `OTR_G_MTX_OTR`, `RDP_G_TRI1_WIDE`, and more) that the interpreter receives at runtime, so game-side source is edited to emit them ([LUS `include/fast/lus_gbi.h`](https://github.com/HarbourMasters/libultraship/blob/main/include/fast/lus_gbi.h)). Second, fidelity is bounded and degrades gracefully: unknown opcodes are logged as critical and skipped in LUS, and silently ignored in sm64ex's `switch` (which has no `default`), while LOD is faked and coverage bits are ignored ([LUS `interpreter.cpp`](https://github.com/HarbourMasters/libultraship/blob/main/src/fast/interpreter.cpp); [sm64ex `gfx_pc.c`](https://github.com/sm64pc/sm64ex/blob/master/src/pc/gfx/gfx_pc.c)). Static recompilation still needs a renderer for the same command stream: Zelda64Recomp uses RT64 to turn N64 display lists into DirectX 12 or Vulkan calls, and RSPRecomp statically recompiles the audio and JPEG microcode ([Zelda64Recomp README](https://github.com/Zelda64Recomp/Zelda64Recomp); [Zelda64Recomp BUILDING.md](https://github.com/Zelda64Recomp/Zelda64Recomp/blob/dev/BUILDING.md)). Necessary: a command-stream interpreter plus a header-level macro layer for register writes. Optional: exact RDP fidelity (LOD approximation and ignored coverage are accepted costs).

## Pointer width and struct layout: the sm64 "fully declared structs" story is false

The claim that sm64 reached 64-bit because its structs are fully declared with no explicit padding is **wrong on both clauses**, and this is the correction most likely to mislead an architecture decision. sm64 has explicit padding fields (`u8 filler[4]`, renamed `u8 padding[4]` in the port), declares address values as integers (`typedef uintptr_t GeoLayout; typedef uintptr_t LevelScript; typedef uintptr_t BehaviorScript;`), gates layout on pointer width with `#if IS_64_BIT`, and ships a helper macro specifically to scale hardcoded 32-bit sizes, `#define DOUBLE_SIZE_ON_64_BIT(size) ((size) * (sizeof(void *) / 4))` ([n64decomp/sm64 `include/types.h`](https://github.com/n64decomp/sm64/blob/master/include/types.h); [sm64-port `include/types.h`](https://github.com/sm64-port/sm64-port/blob/master/include/types.h); [n64decomp/sm64 `include/platform_info.h`](https://github.com/n64decomp/sm64/blob/master/include/platform_info.h)). In `struct Object`, the raw-data union of pointer arrays, `void *asVoidPtr[0x50]`, is compiled out under `#if !IS_64_BIT` and a separate `ptrData` union is added under `#if IS_64_BIT`, precisely because 0x50 pointers do not fit in the 0x140-byte payload on a 64-bit host ([n64decomp/sm64 `include/types.h`](https://github.com/n64decomp/sm64/blob/master/include/types.h)). The N64 comment offsets are stale on 64-bit and are allowed to be: `struct GraphNode` grows from 0x14 to 0x24 as its pointers widen, and the port accepts that ([sm64-port `include/types.h`](https://github.com/sm64-port/sm64-port/blob/master/include/types.h)).

The same lesson appears inside LUS itself, which proves that full declaration is not sufficient. LUS defines display-list words as `uintptr_t` rather than `uint32_t`, so the `Gfx` struct doubles: it "has a size of `0x8` on 32bit and a size of `0x10` on 64bit," which invalidates hardcoded N64 offsets such as `0x0C000010` and forces the port to derive constants from layout at compile time, `((0x0E000000 + offsetof(GfxMasterList, member)) | 1)` ([2ship2harkinian issue #137](https://github.com/HarbourMasters/2ship2harkinian/issues/137); [2ship2harkinian `mm/include/macros.h`](https://github.com/HarbourMasters/2ship2harkinian/blob/045edd624f93a7d1e793312514d2a4c6a77dc3cb/mm/include/macros.h)). The porting guide lists "64-bit Fixes: Address pointer size differences" as an expected step ([libultraship Porting Guide](https://libultraship.com/PORTING)).

What actually enabled 64-bit was not declaration discipline but the absence of a requirement for exact byte offsets, except in two places: persisted save data and the display-list word. sm64 compiles LP64, lets struct layout change, keeps address values in `uintptr_t`, and specially handles the byte-sensitive cases. Endianness is split the same way: the renderer byte-swaps texture data by hand ("Big endian load"), while bulk assets are converted at export time so game logic does no swapping ([sm64-port `gfx_pc.c`](https://github.com/sm64-port/sm64-port/blob/master/src/pc/gfx/gfx_pc.c); [libultraship Porting Guide](https://libultraship.com/PORTING)). The decisive question for the Pokemon Black port is therefore not "32-bit versus 64-bit" but "which structs must have exact byte layout, and why." Pinning layout with something like `u8 pad[0x14]` is a choice that forces ILP32, not a necessity demonstrated by sm64. No sm64 or LUS document states why 64-bit was chosen; the "fully declared" rationale appears to originate with the port project itself, not with sm64 ([gap, notes]).

## Audio and saves: two philosophies, neither forces console emulation

Audio is reimplemented at the microcode command-set level as C, not by running the console microcode. The decompiled synthesis code (`synthesis.c` in sm64, `audio_synthesis.c` in SoH) is compiled essentially unchanged; the port `#undef`s the RSP ABI macros (`aEnvMixer`, `aResample`, `aADPCMdec`, and the rest) and redefines each to call a C DSP function, so commands execute inline against a modelled DMEM instead of being queued to the RSP ([sm64ex `src/pc/mixer.h`](https://github.com/sm64pc/sm64ex/blob/nightly/src/pc/mixer.h); [sm64ex `src/pc/mixer.c`](https://github.com/sm64pc/sm64ex/blob/nightly/src/pc/mixer.c); [SoH `soh/soh/mixer.h`](https://github.com/HarbourMasters/Shipwright/blob/develop/soh/soh/mixer.h)). Both reproduce the hardware `resample_table[64][4]` interpolation coefficients and offer SSE/NEON/AVX2 fast paths, aiming for sample-accurate output ([sm64ex `src/pc/mixer.c`](https://github.com/sm64pc/sm64ex/blob/nightly/src/pc/mixer.c); [SoH `soh/soh/mixer.c`](https://github.com/HarbourMasters/Shipwright/blob/develop/soh/soh/mixer.c)). Crucially, LUS does **not** implement N64 audio: its guide states that LUS "only exposes PC audio drivers" and "your port is responsible for implementing the game's audio pipeline" ([LUS docs/PORTING.md](https://github.com/Kenix3/libultraship/blob/main/docs/PORTING.md)). Audio is a per-game engine. Static recompilation handles this differently and more automatically: RSPRecomp translates the `aspMain` audio microcode ahead of time ([Zelda64Recomp BUILDING.md](https://github.com/Zelda64Recomp/Zelda64Recomp/blob/dev/BUILDING.md)).

Saves split into two opposing designs. sm64ex writes the raw console struct image as a byte-exact 512-byte EEPROM image with the original magics and checksum, byte-swapping to big-endian on little-endian hosts so the file matches a real N64 dump; on load it detects a big-endian console save and swaps it in (an optional `TEXTSAVES` build writes human-editable text instead) ([sm64ex `src/game/save_file.c`](https://github.com/sm64pc/sm64ex/blob/nightly/src/game/save_file.c); [sm64ex `src/game/save_file.h`](https://github.com/sm64pc/sm64ex/blob/nightly/src/game/save_file.h); [sm64ex `SAVE_FORMAT.MD`](https://github.com/sm64pc/sm64ex/blob/nightly/SAVE_FORMAT.MD)). SoH goes the other way: its native format is versioned per-section JSON, and it treats the console SRAM image as a legacy import that `ConvertFromUnversioned` parses by exact slot layout ([SoH `soh/SaveManager.cpp`](https://github.com/HarbourMasters/Shipwright/blob/develop/soh/soh/SaveManager.cpp)). Static recompilation inherits save compatibility from the runtime layer (`librecomp` handles EEPROM/SRAM/Flashram), not from game code ([N64ModernRuntime README](https://github.com/N64Recomp/N64ModernRuntime)).

The practical rule both ecosystems converge on is "match the console where it is observable, abstract where it is not." Observable artifacts (ROM bytes, struct layouts, save images with their magics, checksums, and endianness, resource binary formats) are kept identical; non-observable hardware (VI timing, RSP internals, the scheduler) is freely reimplemented ([2ship2harkinian issue #137](https://github.com/HarbourMasters/2ship2harkinian/issues/137); [libultraship Porting Guide](https://libultraship.com/PORTING)). Note the sourcing limit: the "O2R format must match exactly" statement traces to a search-indexed copy of a doc whose live URL now 404s, and no primary source states a blanket byte-identical charter, so treat that as a gap, not a documented rule ([the-harbour O2R format doc, search-indexed, 404 on fetch](https://github.com/garrettjoecox/the-harbour/blob/main/docs/ship-of-harkinian/o2r-format/index.md)).

## The DS reads hardware back, a burden no N64 port ever carried

This is the one place where the Nintendo DS is genuinely harder than the N64, and it decides whether a register file is needed. N64 graphics give the game no readback path: the GBI is a forward-only command stream, and the ports never had to expose a readable register set. The entire N64 graphics precedent validates the "engine from state" half of a register-file design, not the "readable register file" half. The Nintendo DS is closer to a memory-mapped peripheral. Its game code polls `DISPCNT`, `VCOUNT`, and `DISPSTAT`, reads VRAM, OAM, and palette contents, queries BG and OBJ registers, and synchronizes on scanline state, so a correct native port must answer reads as well as accept writes.

That means a DS port needs a register file with read hooks, plus the same header-level write macros that let matched C compile unchanged. The architecture that follows from the N64 precedent is: define a console-shaped input contract (register writes routed through drop-in macros, exactly as LUS supplies `gbi.h` and `gSP*`/`gDP*` route to the interpreter), back it with a register file that supports readback, and define a native output contract (GPU draw calls) behind one interface. The register file is a superset of what any N64 port implemented; no N64 port is a precedent for the read half. Prior research is thin here, because sm64ex's and LUS's searches for MMIO write-hook abstractions returned none, and the ports do not map the N64 physical register ranges at all ([gap, notes]).

The DS static-recompilation ecosystem confirms the difficulty from a different angle, and its answer is different from a decomp port's. NDS recompilers are real but immature and are hybrids: `mstan/ndsrecomp` "lifts guest ARM code to C ahead of time" but "code copied into RAM by the guest currently uses a bounded interpreter tier," and a related mirror states that the runtime preserves "the original ROM addresses… as the runtime's address space" and reads live opcodes as a fallback ([mstan/ndsrecomp](https://github.com/mstan/ndsrecomp); [Myth7x/ndsrecomp](https://github.com/Myth7x/ndsrecomp)). That approach keeps the address space, which is one way to satisfy readback; a decompilation port compiles matched C and instead needs the register file. The ecosystem author notes the DS shares the GBA's recompilation upsides, with Super Mario 64 DS and Metroid Prime Hunters demos, "neither game… publicly released yet" ([1379.tech ecosystem update](https://1379.tech/building-enhancing-recomps-ecosystem-updates/)). An aggregator lists a single DS recomp entry, Metroid Prime Hunters; treat that count as unverified ([FanGamesDB recomps survey](https://fangamesdb.com/recomps.html)).

On the Pokemon Black source itself, the notes carried two stale citations, both corrected here. `pokemodding/pokeblack` now redirects to **`squiddonaut/pokeblack`**, "a decompilation of English Pokemon Black (NDS)" that builds `pokeblack.us.nds` with sha1 `26ad0b9967aa279c4a266ee69f52b9b2332399a5`, and it sits at **0.03% matched** on decomp.dev, below decomp.dev's own 0.5% display threshold ([squiddonaut/pokeblack](https://github.com/squiddonaut/pokeblack); [decomp.dev](https://decomp.dev/squiddonaut/pokeblack)). `Goldoire/pokeblack` returns 404 and is dropped as a dead citation. And the `pret` organization has no Black or White decompilation; its DS lineup stops at Generation 4 (pokediamond, pokeplatinum, pokeheartgold), so no `pret` Black project exists ([pret/pokediamond](https://github.com/pret/pokediamond); [pret/pokeplatinum](https://github.com/pret/pokeplatinum)). That 0.03% figure belongs to `squiddonaut/pokeblack`, a separate, independent effort on the same ROM, not to the decompilation this report serves. The project this report serves is a local decompilation called aletheia, targeting the exact same ROM (`sha1 26ad0b9967aa279c4a266ee69f52b9b2332399a5`, Pokemon Black USA/Europe NDSi Enhanced), and it is essentially code complete: **33,524 matched `.c` files** under `src/matched`, **2,183,286 of 2,183,302 game code bytes matched** (99.9993% of game), **98.99% of game code and 99.20% of all code fully linked**, **181 of 243 regions linking byte-identical**, and gamecheck reporting **35,520 functions with 0 missing and 0 doubled**. The byte-verified surface to compile is therefore nearly the whole game, not a tiny fragment, and the address-space, register-file, and SDK-shim decisions can be made against a code-complete target. That is the same position sm64-port and Ship of Harkinian were in, since both started only after their decompilations reached code completion ([Gaming Reinvented, 2019](https://gamingreinvented.com/news/super-mario-64-has-been-completely-decompiled-source-code-available/); [Wikipedia, Ship of Harkinian](https://en.wikipedia.org/wiki/Ship_of_Harkinian)).

## Keeping decompiled source unedited is a convention, not a rule

No written rule in either project family says "do not edit matched files" or "portability belongs in the port layer." The only written porting rules point the opposite way: the libultraship guide explicitly instructs editing the decompilation (replace includes, stub functions, disable systems) ([libultraship Porting Guide](https://libultraship.com/PORTING)). The de facto discipline is structural and differs sharply between the two families. sm64-port is a GitHub fork of the decomp that keeps the decomp tree, adds a `src/pc` port layer, filters out `src/game/main.c` in favor of its own entry point, and guards divergence with the decomp's own `TARGET_N64`/`NON_MATCHING`/`AVOID_UB` defines; the N64 matching build and SHA-1 check are retained, and port builds force `COMPARE := 0` so no re-verify is attempted because PC edits are compiled out of the N64 target ([sm64-port `Makefile`](https://github.com/sm64-port/sm64-port/blob/master/Makefile); [sm64-port `src/pc`](https://github.com/sm64-port/sm64-port/tree/master/src/pc)). Ship of Harkinian abandons this: it vendors an **edited** copy of the OoT decomp at `soh/` (a subrepo of a HarbourMasters fork with `method = rebase`), holds its own port code at `soh/soh`, depends on the `libultraship` SDK shim as a submodule, builds no N64 ROM at all, and enforces fidelity only at runtime through toggles so you "can play it in all of its 1998 glory" ([Shipwright `soh/.gitrepo`](https://github.com/HarbourMasters/Shipwright/blob/develop/soh/.gitrepo); [Shipwright `.gitmodules`](https://github.com/HarbourMasters/Shipwright/blob/develop/.gitmodules); [shipofharkinian.com](https://www.shipofharkinian.com)). Only the sm64 model permits byte-match re-verification; SoH's model structurally precludes it.

Divergence has a real, visible cost in both models. sm64-port tracks a numbered "Refresh" merge log up to Refresh 14, folding in upstream decomp refactors and relabels, and its `CHANGES` records "No more nonmatchings remain for US, JP, or EU builds" at Refresh 13 ([sm64-port `CHANGES`](https://github.com/sm64-port/sm64-port/blob/master/CHANGES)). The sm64ex fork drifted out of sync with the official port ([r/SM64PC breakdown, 2020](https://www.reddit.com/r/SM64PC/comments/hhv0h1/super_mario_64_port_and_the_sm64ex_fork_breakdown)). A directly analogous SSB64 port migrated its vendored decomp into a submodule on a `port-patches` branch, deleted 1031 vendored files, and added semantic-equivalence auditing tools reporting "446 / 475 TUs byte-identical… 0 structural divergence," explicitly to enable "future upstream sync" ([JRickey/BattleShip PR #129](https://github.com/JRickey/BattleShip/pull/129)). The practical reading: the "no edits to matched files" discipline is optional, and what genuinely matters is that any divergence stays separable and reconcilable. Static recompilation has its own version of this: mods replace whole functions (patched functions marked `RECOMP_PATCH`), and ordinary linker symbol priority lets patches win over recompiler output ([N64Recomp README](https://github.com/N64Recomp/N64Recomp); [DeepWiki: Zelda64Recomp Recompilation System](https://deepwiki.com/Zelda64Recomp/Zelda64Recomp/3.1-recompilation-system), AI-generated, secondary).

## Conclusion

The decision that this evidence actually settles is not "emulate the DS or not" but "which console behaviors are observable to game code." Nothing observable to the CPU's instruction stream needs a console address space: the mature ecosystems all compile addresses away and reimplement the SDK, and the one place they invest in interpretation is the graphics command stream, because that is the one artifact the game generates at runtime and cannot hand off to a library call. For a native Pokemon Black port, that means the graphics interpreter is necessary, the register file with readback is necessary (and is the piece with no N64 precedent, because the DS reads registers back and the N64 never did), the SDK shim is necessary but is an own-your-code responsibility that LUS itself delegates for audio, while address-space emulation and save-file byte compatibility are optional layers you choose only if you need emulator or hardware interop.

The second thing this evidence changes is sequencing. The requester's decompilation is code complete (33,524 matched `.c` files, 99.9993% of game code bytes matched, 181 of 243 regions byte-identical), so they are in the same position as sm64-port and Ship of Harkinian, both of which started only after their decompilations reached code completion ([Gaming Reinvented, 2019](https://gamingreinvented.com/news/super-mario-64-has-been-completely-decompiled-source-code-available/); [Wikipedia, Ship of Harkinian](https://en.wikipedia.org/wiki/Ship_of_Harkinian)). The sequencing point that survives is that a code-complete decomp keeps being renamed and restructured by cleanup work, which is exactly the tail that drives sm64-port's recurring "Refresh" merges, so the divergence mechanism (how port edits stay separable and reconcilable from upstream) remains the highest-leverage choice, not the fidelity of any single artifact. And on pointer width, the reasoning should not lean on the sm64 myth: sm64 proves that you can compile LP64 and let layout change only because almost nothing it persists needs exact offsets, so the honest question for Black is which of its `u8 pad[...]`-pinned structs must survive byte-exact, and whether keeping an N64-style matching target (the sm64 model) is worth the recurring refresh merges it costs ([sm64-port `CHANGES`](https://github.com/sm64-port/sm64-port/blob/master/CHANGES)).

| Console-specific artifact | What the mature ports do | Genuinely necessary? |
|---|---|---|
| Console address space | Neutralized to identity casts and host pointers (`-DNO_SEGMENTED_MEMORY`, `PHYSICAL_TO_VIRTUAL` identity); no MMU, no per-address helper ([sm64-port `Makefile`](https://github.com/sm64-port/sm64-port/blob/master/Makefile)) | No |
| MMIO / hardware registers | No register file for graphics; device access reimplemented as SDK functions; N64 game code rarely touches mapped registers ([Mr-Wiseguy, issue #26](https://github.com/Mr-Wiseguy/N64Recomp/issues/26)) | Yes for DS, because game code reads registers back |
| Graphics command stream | Interpreted at the opcode level (`gfx_run_dl`, `gfx_step`); game's DL-building C runs unchanged against drop-in `gbi.h` macros ([LUS `interpreter.cpp`](https://github.com/HarbourMasters/libultraship/blob/main/src/fast/interpreter.cpp)) | Yes |
| Console SDK | Reimplemented as a header-compatible host library ("compile-time WINE"); many VI/cache functions are empty stubs ([libultraship Porting Guide](https://libultraship.com/PORTING); [LUS `os_vi.cpp`](https://github.com/HarbourMasters/libultraship/blob/main/src/libultraship/libultra/os_vi.cpp)) | Yes, but you own the parts LUS does not cover (audio) |
| Pointer width / struct layout | Compile LP64 and let layout change; parameterize on `IS_64_BIT`/`DOUBLE_SIZE_ON_64_BIT`; only saves and DL words need exact bytes ([n64decomp `platform_info.h`](https://github.com/n64decomp/sm64/blob/master/include/platform_info.h)) | Only for byte-sensitive structs; pinning everything to ILP32 is a choice |
| Audio | HLE the microcode command set as C (`#undef` macros to immediate calls); LUS supplies drivers only, audio is per-game ([sm64ex `mixer.c`](https://github.com/sm64pc/sm64ex/blob/nightly/src/pc/mixer.c); [LUS docs/PORTING.md](https://github.com/Kenix3/libultraship/blob/main/docs/PORTING.md)) | Yes, if audio fidelity matters; engine is yours |
| Save files | sm64ex keeps a byte-exact big-endian EEPROM image; SoH uses JSON with a console-import bridge ([sm64ex `save_file.c`](https://github.com/sm64pc/sm64ex/blob/nightly/src/game/save_file.c); [SoH `SaveManager.cpp`](https://github.com/HarbourMasters/Shipwright/blob/develop/soh/soh/SaveManager.cpp)) | Optional; needed only for emulator/hardware interop |
| Keeping matched C unedited | No written rule; sm64-port keeps the N64 build and guards edits, SoH edits a vendored decomp and cannot re-verify ([sm64-port `Makefile`](https://github.com/sm64-port/sm64-port/blob/master/Makefile); [Shipwright `soh/.gitrepo`](https://github.com/HarbourMasters/Shipwright/blob/develop/soh/.gitrepo)) | Optional; what matters is keeping divergence separable |
