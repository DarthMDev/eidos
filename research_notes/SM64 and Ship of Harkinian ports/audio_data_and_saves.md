# How sm64ex and Ship of Harkinian Handled N64 Audio, Saves, and Data Fidelity

Scope note: this covers the **Super Mario 64 PC port** (`sm64pc/sm64ex`, branch `nightly`, descended from `sm64-port/sm64-port`) and **Ship of Harkinian** (HarbourMasters/Shipwright, branch `develop`) with its **libultraship (LUS)** SDK-reimplementation library. All findings come from the projects' own source trees (fetched via `git show` from blobless clones), which are cited with GitHub URLs.

---

## Q1: How did they reimplement N64 audio? Did they interpret the microcode command stream, or work at a higher level? Name the code.

### Takeaway
Both ports reimplement the N64 audio **at the RSP microcode "ABI-command" level as C functions**, not by running the `aspMain` microcode and not by replacing the synthesis with a friendlier high-level engine. The decompiled game code (`synthesis.c` / `audio_synthesis.c`) is compiled essentially unchanged; the macro layer that used to append commands to an RSP command list is `#undef`'d and redefined to call the port's C DSP implementations, so the "command list" executes inline. The audio engine lives **in the game port**, not in libultraship (LUS only supplies output drivers).

### Cited Findings
- On the N64, the application's audio library builds a command list that is processed by the RSP **Audio Synthesis Microcode**, which produces stereo 16-bit samples fed to the Audio DACs — "The Audio Synthesis Microcode processes the tasks passed to it by the application and synthesizes stereo 16-bit samples" ([N64 Programming Manual, ch.17 Audio](https://ultra64.ca/files/documentation/online-manuals/man/pro-man/pro17/index.html)); the RSP "is the microcode engine that executes audio and graphics tasks" ([N64 Programming Manual 3.2 Reality CoProcessor](https://ultra64.ca/files/documentation/online-manuals/man/pro-man/pro03/index3.2.html)); N64 SDK audio came in two microcode variants, `aspMain.o` and `n_aspMain.o` ([N64 Programming Manual ch.6 Audio](https://ultra64.ca/files/documentation/online-manuals/man/nusystem/tutorial/6.htm)).
- sm64ex's game-side synthesis code (`src/audio/synthesis.c`) is a decompilation of the *application* side: it emits RSP ABI commands via macros (`aSetBuffer`, `aLoadBuffer`, `aADPCMdec`, `aResample`, `aEnvMixer`, `aMix`, `aInterleave`, `aSaveBuffer`, …) and contains no RSP execution ([sm64ex src/audio/synthesis.c](https://github.com/sm64pc/sm64ex/blob/nightly/src/audio/synthesis.c)).
- That file includes the port's mixer header: `#include "../pc/mixer.h"` ([sm64ex src/audio/synthesis.c includes](https://github.com/sm64pc/sm64ex/blob/nightly/src/audio/synthesis.c)).
- sm64ex `src/pc/mixer.h` `#undef`s the ABI macros from `<PR/abi.h>` (`aSegment`, `aClearBuffer`, `aSetBuffer`, `aLoadBuffer`, `aSaveBuffer`, `aDMEMMove`, `aMix`, `aEnvMixer`, `aResample`, `aInterleave`, `aSetVolume`, `aSetLoop`, `aLoadADPCM`, `aADPCMdec`) and redefines each to call a C function (e.g. `aEnvMixer(pkt,f,s) → aEnvMixerImpl(f,s)`; `aSegment` becomes a no-op) ([sm64ex src/pc/mixer.h](https://github.com/sm64pc/sm64ex/blob/nightly/src/pc/mixer.h)).
- sm64ex `src/pc/mixer.c` implements those commands as real DSP C code: `aClearBufferImpl`, `aLoadBufferImpl`, `aSaveBufferImpl`, `aLoadADPCMImpl`, `aSetBufferImpl`, `aSetVolumeImpl`, `aInterleaveImpl`, `aDMEMMoveImpl`, `aSetLoopImpl`, `aADPCMdecImpl`, `aResampleImpl`, `aEnvMixerImpl`, `aMixImpl`, with a static `rspa` state struct (DMEM buffer, ADPCM table, pointers, vol/rate) and the hardware `resample_table[64][4]` interpolation coefficients ([sm64ex src/pc/mixer.c](https://github.com/sm64pc/sm64ex/blob/nightly/src/pc/mixer.c)). It has SSE4.1 and ARM-NEON fast paths ([sm64ex src/pc/mixer.c](https://github.com/sm64pc/sm64ex/blob/nightly/src/pc/mixer.c)).
- Ship of Harkinian takes the identical approach with its own engine in `soh/soh/mixer.c` + `soh/soh/mixer.h`, included by the decompiled synthesis code (`soh/src/code/audio_synthesis.c`: `#include "soh/mixer.h"`) and by `soh/src/code/code_800F9280.c` ([SoH mixer.h](https://github.com/HarbourMasters/Shipwright/blob/develop/soh/soh/mixer.h); the include sites appear in [audio_synthesis.c](https://github.com/HarbourMasters/Shipwright/blob/develop/soh/src/code/audio_synthesis.c) and [code_800F9280.c](https://github.com/HarbourMasters/Shipwright/blob/develop/soh/src/code/code_800F9280.c)).
- SoH's mixer covers a **wider** command set consistent with OoT's audio microcode: `aEnvSetup1Impl`, `aEnvSetup2Impl`, `aEnvMixerImpl`, `aAddMixerImpl`, `aFilterImpl`, `aHiLoGainImpl`, `aS8DecImpl`, `aResampleZohImpl`, `aDuplicateImpl`, `aInterlImpl`, `aUnkCmd3Impl`, `aUnkCmd19Impl`, plus `aOPUSdecImpl`/`aOPUSFree` for custom (mod) audio ([SoH soh/soh/mixer.h](https://github.com/HarbourMasters/Shipwright/blob/develop/soh/soh/mixer.h); implementations in [soh/soh/mixer.c](https://github.com/HarbourMasters/Shipwright/blob/develop/soh/soh/mixer.c)).
- SoH's mixer has reference, SSE2, NEON and AVX2 versions of the hot `aMix` path ([SoH soh/soh/mixer.c](https://github.com/HarbourMasters/Shipwright/blob/develop/soh/soh/mixer.c)).
- SoH **retains the game's audio-manager/task pipeline**: `AudioMgr_HandleRetrace` still builds an `AudioTask` and sends it to the scheduler (`osSendMesgPtr(&audioMgr->sched->cmdQ, …)`) ([SoH src/code/audioMgr.c](https://github.com/HarbourMasters/Shipwright/blob/develop/soh/src/code/audioMgr.c)).
- SoH produces PCM on a **native host thread**: `OTRAudio_Thread()` repeatedly calls `AudioMgr_CreateNextAudioBuffer(...)` and then `AudioPlayer_Play(buf, len)`, which forwards to LUS `AudioPlayerPlayFrame` ([SoH soh/OTRGlobals.cpp](https://github.com/HarbourMasters/Shipwright/blob/develop/soh/soh/OTRGlobals.cpp); the buffer generator is [code_800E4FE0.c `AudioMgr_CreateNextAudioBuffer`](https://github.com/HarbourMasters/Shipwright/blob/develop/soh/src/code/code_800E4FE0.c)).
- LUS itself only provides **output backends**, not N64 audio: it exposes SDL / CoreAudio / WASAPI / Null players ([LUS Audio.cpp](https://github.com/HarbourMasters/libultraship/blob/main/src/ship/audio/Audio.cpp); [AudioPlayer headers](https://github.com/HarbourMasters/libultraship/blob/main/include/ship/audio/AudioPlayer.h)). LUS's own porting guide states: "LUS only exposes PC audio drivers — it does not interface with N64 audio… Your port is responsible for implementing the game's audio pipeline and routing its output through one of these drivers" ([LUS docs/PORTING.md](https://github.com/Kenix3/libultraship/blob/main/docs/PORTING.md)).
- sm64ex's N64-side audio shim is `osAiSetFrequency`, which reproduces the Audio Interface's clock/divisor math (`D_8033491C / freq`, the `& 0xff`/`>16` clamps) rather than using a real AI ([sm64ex src/pc/ultra_reimplementation.c](https://github.com/sm64pc/sm64ex/blob/nightly/src/pc/ultra_reimplementation.c)); PCM output is handled by the platform audio API/backends in `src/pc/audio/` (`audio_api.h`, `audio_sdl2.c`, `audio_sdl1.c`, `audio_null.c`) ([sm64ex src/pc/audio/](https://github.com/sm64pc/sm64ex/tree/nightly/src/pc/audio)).
- The SM64 port openly documents that its audio subsystem is not fully decompiled: "This repo contains a full decompilation of Super Mario 64 (J), (U), and (E) **with minor exceptions in the audio subsystem**" ([sm64-port README](https://github.com/sm64-port/sm64-port)). The decompilation's craft notes describe sequences as ".m64 format… similar to MIDI, but Turing complete" and samples as custom ADPCM AIFF ([n64decomp/sm64 sound/README.md](https://github.com/n64decomp/sm64/blob/master/sound/README.md)).

### Inferences
- Mechanism: because `synthesis.c`/`audio_synthesis.c` include `mixer.h`, the ports do **not** maintain a command buffer for audio. Each `aXXX` call now executes immediately against the mixer's DMEM model (`rspa`). This is high-level emulation (HLE) of the microcode's *command set*, i.e. exactly "interpret/execute the audio command stream," rather than emulating the RSP instruction set or reimplementing at a higher (MIDI/synth) level.
- The `resample_table[64][4]` values are a fixed-point interpolation table characteristic of the N64 audio microcode; reproducing it indicates the ports aim for sample-accurate output rather than approximate mixing.
- Because LUS explicitly does not implement N64 audio, the audio engine is a per-game responsibility — so a future DS port (eidos) should expect the same: reimplement the ARM7/audio codec "command" layer natively, not the SDK.

### Gaps
- I did not find documentation naming the **provenance/author** of the `mixer.c` DSP implementations beyond the project credits ("Kenix … Audio System Programmer" in the [SoH README](https://github.com/HarbourMasters/Shipwright/blob/develop/README.md)); no primary source describes the porting methodology of the mixer in prose.
- I could not confirm in source whether sm64ex implements `osAiSetNextBuffer`/`osAiGetLength` in `platform.c` or elsewhere; only `osAiSetFrequency` was verified (grep of `ultra_reimplementation.c`). SoH does implement `osAiGetLength`/`osAiSetNextBuffer` in LUS ([os.cpp](https://github.com/HarbourMasters/libultraship/blob/main/src/libultraship/libultra/os.cpp)).

## Q2: What is the equivalent SDK shim layer (file access, allocation, threads, timing)? How much is reimplemented vs. stubbed?

### Takeaway
Both ports replace the libultra OS/VI/AI/PI/EEPROM surface with host C/C++ shims and let the game's own logic run on top. **sm64ex** does this in one file, `src/pc/ultra_reimplementation.c`, plus a virtual filesystem (`src/pc/fs/`). **SoH** routes the same through **libultraship's `src/libultraship/libultra/`** (os.cpp, os_pi.cpp, os_eeprom.cpp, os_cache.cpp, os_time.cpp, os_vi.cpp, os_vm.cpp, os_mesg.cpp, AudioDmaRegistry.cpp). Many functions are outright **stubs/no-ops** (VI/video, cache ops, message queues), and LUS's own guide tells porters to *stub* things LUS handles automatically (it names `osCreateThread`).

### Cited Findings
- sm64ex's shim file reimplements or stubs: `osPiStartDma`, `osCreateMesgQueue`, `osSetEventMesg`, `osJamMesg`, `osSendMesg`, `osRecvMesg`, `osVirtualToPhysical`, `osCreateViManager`, `osViSetMode`, `osViSetEvent`, `osViBlack`, `osViSetSpecialFeatures`, `osViSwapBuffer`, `osGetTime`, `osWritebackDCacheAll`, `osWritebackDCache`, `osInvalDCache`, `osGetCount`, `osAiSetFrequency`, `osEepromProbe`, `osEepromLongRead`, `osEepromLongWrite` ([sm64ex src/pc/ultra_reimplementation.c](https://github.com/sm64pc/sm64ex/blob/nightly/src/pc/ultra_reimplementation.c)).
- Several of these are markered `UNUSED` and are effectively no-ops (e.g. `osViSetMode`, `osViBlack`, `osWritebackDCache`, `osInvalDCache`, `osCreateViManager`) — i.e. stubbed, not emulated ([sm64ex src/pc/ultra_reimplementation.c](https://github.com/sm64pc/sm64ex/blob/nightly/src/pc/ultra_reimplementation.c)).
- `osVirtualToPhysical` is reimplemented as the identity/`K0_TO_PHYS`-style conversion so N64-address code keeps working ([sm64ex src/pc/ultra_reimplementation.c](https://github.com/sm64pc/sm64ex/blob/nightly/src/pc/ultra_reimplementation.c)).
- SoH's shim layer is libultraship's `src/libultraship/libultra/`. `os.cpp` reimplements `osContInit`, `osContStartReadData`, `osContGetReadData`, `osSetTime`/`osGetTime`/`osGetCount`, `osCartRomInit`, `osSetTimer`, `osEPiStartDma`, `osAiGetLength`, `osAiSetNextBuffer`, `__osMotorAccess`, `osMotorInit` ([LUS os.cpp](https://github.com/HarbourMasters/libultraship/blob/main/src/libultraship/libultra/os.cpp)).
- LUS `os_eeprom.cpp` implements `osEepromProbe`→`EEPROM_TYPE_4K`, and `osEepromLongRead`/`osEepromLongWrite` as a 512-byte `default.sav` file, including the same 8-byte-per-address mapping as the console (`content + address * 8`) ([LUS os_eeprom.cpp](https://github.com/HarbourMasters/libultraship/blob/main/src/libultraship/libultra/os_eeprom.cpp)).
- LUS `os_pi.cpp` reimplements `osPiStartDma` and, because ported audio samples are host blobs rather than cartridge addresses, registers audio "blob" ranges and **clamps DMA reads to the blob size** via `AudioDma_Register`/`AudioDma_Clamp` ([LUS os_pi.cpp](https://github.com/HarbourMasters/libultraship/blob/main/src/libultraship/libultra/os_pi.cpp); [AudioDmaRegistry.cpp](https://github.com/HarbourMasters/libultraship/blob/main/src/libultraship/libultra/AudioDmaRegistry.cpp)). The comment says DMA "reads fixed-size chunks that can extend past the blob."
- LUS is explicitly framed as the SDK shim: "libultraship (LUS) is a library meant to provide reimplementations of libultra (n64 sdk) functions that run on modern hardware" ([LUS README](https://github.com/HarbourMasters/libultraship/blob/main/README.md)); "LUS is designed to mimic the functionality of libultra on modern hardware" ([SoH README](https://github.com/HarbourMasters/Shipwright/blob/develop/README.md)).
- LUS's porting guide frames it as "compile-time WINE for the N64," and instructs porters to "Comment out or stub functions that LUS handles automatically (e.g., **osCreateThread** for rumble, as LUS manages threads differently than the N64 CPU)" ([LUS docs/PORTING.md](https://github.com/Kenix3/libultraship/blob/main/docs/PORTING.md)).
- Allocation/heap: neither shim file implements a `OS_AllocFromHeap`-style OS heap. SM64's own heap is in the game (`src/engine`), and the port compiles the decomp's `lib/` for math/audio helpers only, e.g. `lib/src/alBnkfNew.c`, `lib/src/guMtxF2L.c`, `lib/src/ldiv.c`, `lib/src/hardware.h`, `lib/src/libaudio_internal.h`, `lib/src/osAi.h`, `lib/src/osContInternal.h` ([sm64ex lib/src listing](https://github.com/sm64pc/sm64ex/tree/nightly/lib/src)).
- Timing: sm64ex reimplements `osGetTime`/`osGetCount` against host time ([sm64ex src/pc/ultra_reimplementation.c](https://github.com/sm64pc/sm64ex/blob/nightly/src/pc/ultra_reimplementation.c)); SoH/LUS reimplements `osGetTime`/`osSetTime`/`osGetCount`/`osSetTimer` ([LUS os.cpp](https://github.com/HarbourMasters/libultraship/blob/main/src/libultraship/libultra/os.cpp)). SoH uses an `R_UPDATE_RATE`/interpolation setting to pick PCM frame sizes and runs audio on its own thread ([SoH soh/OTRGlobals.cpp](https://github.com/HarbourMasters/Shipwright/blob/develop/soh/soh/OTRGlobals.cpp)).

### Inferences
- The shim layer's design principle is: keep the *ABI and address semantics* of libultra calls (so decompiled code compiles unchanged) but back them with host services; hardware that has no host analogue (VI registers, dcache, physical-address translation) becomes a no-op or identity.
- Threading is deliberately *not* reproduced 1:1 — the N64 scheduler/message-queue model is stubbed/faked while the port drives its own threads (SoH's `OTRAudio_Thread`).

### Gaps
- I found no evidence of an explicit `OS_AllocFromHeap`/`osMemAlloc` shim in either port; the games provide their own heaps. This is the single closest analogue for eidos' `OS_AllocFromHeap` concern and it is **not documented** in the sources reviewed (gap).
- I did not enumerate SoH's `os_cache.cpp`/`os_time.cpp`/`os_vi.cpp`/`os_vm.cpp`/`os_mesg.cpp` bodies, only their existence ([LUS directory](https://github.com/HarbourMasters/libultraship/tree/main/src/libultraship/libultra)).

## Q3: Save files — how is console compatibility preserved? What is the format (struct image, checksum, endianness)? Serializer or direct struct write?

### Takeaway
Two different strategies:
- **sm64ex writes the raw console struct image** (a byte-exact 512-byte EEPROM image), with the original magic numbers and checksum, and **byteswaps to big-endian when running on a little-endian host**, so the file on disk matches a real N64 EEPROM dump. On load it detects a big-endian console save and swaps it in. No serializer for the default path. (An optional `TEXTSAVES` build writes a human-editable text format instead.)
- **SoH natively uses per-section JSON** (`Save/file1.sav`, `Save/global.sav`) rather than a raw image, but it can **import the original N64 SRAM image** (`oot_save.sav`) by parsing the exact console slot layout and converting it to JSON. It also keeps the game's SRAM byte-offset machinery wired to a raw file for the file-select layer.

### Cited Findings
- sm64ex save constants/structs: `EEPROM_SIZE 0x200` (512 bytes), `NUM_SAVE_FILES 4`, `struct SaveBlockSignature { u16 magic; u16 chksum; }`, `struct SaveFile`, `struct SaveBuffer { struct SaveFile files[4][2]; struct MainMenuSaveData menuData[2]; }` (two backup slots per file plus menu backups, padded to 0x200) ([sm64ex src/game/save_file.h](https://github.com/sm64pc/sm64ex/blob/nightly/src/game/save_file.h)).
- Magic values and checksum: `#define MENU_DATA_MAGIC 0x4849`, `#define SAVE_FILE_MAGIC 0x4441`; the checksum is a literal byte sum excluding the two checksum bytes; `add_save_block_signature(...)` writes magic+checksum ([sm64ex src/game/save_file.c](https://github.com/sm64pc/sm64ex/blob/nightly/src/game/save_file.c)).
- sm64ex writes/reads the **struct image directly** to EEPROM via the shim: `write_eeprom_data(...)` calls `osEepromLongWrite(&gSIEventMesgQueue, offset, buffer, size)`, where `offset = baseofs >> 3` (the console's 8-byte EEPROM addressing) ([sm64ex src/game/save_file.c](https://github.com/sm64pc/sm64ex/blob/nightly/src/game/save_file.c)).
- Endianness handling: `write_eeprom_savefile`/`write_eeprom_menudata` byteswap each multi-byte field on little-endian hosts before writing ("Wrappers that byteswap the data on LE platforms before writing it to 'EEPROM'"), while on big-endian they write the struct untouched ([sm64ex src/game/save_file.c](https://github.com/sm64pc/sm64ex/blob/nightly/src/game/save_file.c)).
- Loading: `save_file_load_all()` reads the 512-byte image, then `save_file_need_bswap()` detects a console (big-endian) save by comparing magic against `BSWAP16(magic)`, and `save_file_bswap()` converts it; it validates both slots of each block and rebuilds a corrupt slot from its backup ([sm64ex src/game/save_file.c](https://github.com/sm64pc/sm64ex/blob/nightly/src/game/save_file.c)).
- The EEPROM shim stores a 512-byte image and maps addresses at 8 bytes each: `osEepromLongRead` reads 512 bytes and does `memcpy(buffer, content + address * 8, nbytes)`; `osEepromLongWrite` read-modify-writes the 512-byte buffer ([sm64ex src/pc/ultra_reimplementation.c](https://github.com/sm64pc/sm64ex/blob/nightly/src/pc/ultra_reimplementation.c)).
- Optional text saves: the `TEXTSAVES` build of `save_file_do_save()` calls `write_text_save(fileIndex)` instead of the EEPROM path, using `text_save.inc.h` with `FILENAME_FORMAT "%s/sm64_save_file_%d.sav"` and a TOML-like `key = value` layout documented in `SAVE_FORMAT.MD` ([sm64ex SAVE_FORMAT.MD](https://github.com/sm64pc/sm64ex/blob/nightly/SAVE_FORMAT.MD); [src/game/text_save.inc.h](https://github.com/sm64pc/sm64ex/blob/nightly/src/game/text_save.inc.h); [src/game/save_file.c](https://github.com/sm64pc/sm64ex/blob/nightly/src/game/save_file.c)). This text format is a **host-only** representation, not console-compatible.
- SoH's native format is JSON with per-file sections and a `version` field: `SaveManager::LoadFile` parses `saveBlock` and dispatches `saveBlock["sections"]` to registered `SectionLoadHandler`s; `SaveManager::SaveGlobal` emits `{version, audioSetting, zTargetSetting, language}` to `Save/global.sav` ([SoH soh/SaveManager.cpp](https://github.com/HarbourMasters/Shipwright/blob/develop/soh/soh/SaveManager.cpp)); file paths are `Save/file{N}.sav` ([same file](https://github.com/HarbourMasters/Shipwright/blob/develop/soh/soh/SaveManager.cpp)); community docs confirm saves live in a `/saves/`-style folder named `file#.sav` ([the-harbour casual-save-files.md](https://github.com/garrettjoecox/the-harbour/blob/main/docs/ship-of-harkinian/info/casual-save-files.md)).
- SoH **imports the original console SRAM layout**: `SaveManager::ConvertFromUnversioned()` opens `oot_save.sav`, checks the header magic `{'\0','\0','\0','\x98','\x09','\x10','\x21','Z','E','L','D','A'}` at `SRAM_HEADER_MAGIC`, and computes slot positions as `SLOT_OFFSET(index) = SRAM_HEADER_SIZE + 0x10 + index * (sizeof(SaveContext_v0) + 0x28)`, validating each slot's `ZELDAZ` "new file" magic before converting it to JSON ([SoH soh/SaveManager.cpp](https://github.com/HarbourMasters/Shipwright/blob/develop/soh/soh/SaveManager.cpp)).
- SoH retains a byte-offset SRAM path for the file-select layer: `soh/src/code/z_ss_sram.c` calls `Ctx_WriteSaveFile/Ctx_ReadSaveFile`, which forward to `SaveManager::WriteSaveFile/ReadSaveFile`; these `seekp(addr)`/`seekg(addr)` into the save file and read/write raw bytes ([SoH src/code/z_ss_sram.c](https://github.com/HarbourMasters/Shipwright/blob/develop/soh/src/code/z_ss_sram.c); [SoH soh/OTRGlobals.cpp](https://github.com/HarbourMasters/Shipwright/blob/develop/soh/soh/OTRGlobals.cpp); [soh/SaveManager.cpp](https://github.com/HarbourMasters/Shipwright/blob/develop/soh/soh/SaveManager.cpp)).
- Both games' console save media differ: SM64 uses **EEPROM**, OoT uses **SRAM** (`.sra`); a third-party converter documents "N64 console save format (Big Endian)" vs emulator/Little-Endian formats and states SoH/PC-port `oot_save.sav` binary saves "will automatically convert it to JSON" on load ([ZeldaSaveTool README](https://github.com/xoascf/ZeldaSaveTool)). Community 010 binary templates enumerate SM64-EEPROM and OoT-SRAM layouts ([KilianSteenman/N64-Save-file-formats](https://github.com/KilianSteenman/N64-Save-file-formats)); a dedicated SM64 EEPROM format doc exists at [bryc/sm64eep](https://github.com/bryc/sm64eep).

### Inferences
- sm64ex's default save file **is** the console EEPROM image (big-endian) — so it is interoperable with emulators/DexDrive dumps by construction, and no serialiser is involved: the ported game code writes the in-memory `SaveBuffer` struct straight through the EEPROM shim.
- SoH's philosophy is the opposite: it treats the console image as a **legacy import** and re-encodes the `SaveContext` into versioned JSON sections. Console fidelity is preserved only at the import boundary (`ConvertFromUnversioned`) and in the retained SRAM-offset file path.
- For an eidos-style "keep structs byte-compatible" requirement, sm64ex is the closer model: byte-exact struct image + explicit endianness normalisation + original magic/checksum.

### Gaps
- SoH's `ReadSaveFile`/`WriteSaveFile` target file is `GetSaveFile()`; I could not confirm in source whether that is the same `file{N}.sav` JSON or a separate raw image file (name unverified) ([SoH soh/OTRGlobals.cpp](https://github.com/HarbourMasters/Shipwright/blob/develop/soh/soh/OTRGlobals.cpp)).
- I did not verify whether sm64ex's 512-byte EEPROM image is *bit-for-bit* identical to a DexDrive/raw EEPROM dump including unused filler, only that it writes the `SaveBuffer` struct (which is statically asserted to be `== EEPROM_SIZE`) plus big-endian byteswap ([sm64ex src/game/save_file.c](https://github.com/sm64pc/sm64ex/blob/nightly/src/game/save_file.c), [save_file.h](https://github.com/sm64pc/sm64ex/blob/nightly/src/game/save_file.h)).
- No primary source states whether SoH verifies the N64 SRAM **checksum** on import (the conversion only checks magics).

## Q4: How are assets loaded (ROM filesystem, Yaz0, cartridge layout) and kept compatible?

### Takeaway
Neither port emulates the cartridge filesystem at runtime. **sm64ex extracts assets at build time** and links them into the executable (with a virtual FS used only for add-on resource packs/config/saves). **SoH extracts assets from the ROM at first run/build** into an archive (`oot.o2r` = zip-compatible, `.otr` = MPQ-compatible) and re-serialises each resource into a documented binary layout; the decompiled **Yaz0** decompressor is retained as source in the game code.

### Cited Findings
- sm64ex builds assets in: its `Makefile` compiles `assets`, `levels`, `bin` directories into the binary (`SRC_DIRS := … actors levels bin data assets src/pc …`) ([sm64ex Makefile](https://github.com/sm64pc/sm64ex/blob/nightly/Makefile)); the decomp pipeline uses `extract_assets.py` + `assets.json` to turn ROM data into `.inc.c`/`bin` sources ([sm64ex extract_assets.py / assets.json](https://github.com/sm64pc/sm64ex/tree/nightly)). ROM assets thereby become **compiled-in data**, not runtime files.
- SoH: "Any copyrighted assets are extracted from the ROM and reformatted as a `.otr` archive file which the code uses" ([SoH README](https://github.com/HarbourMasters/Shipwright/blob/develop/README.md)). LUS documents the archive semantics: "`.otr` files are `.mpq` compatible files. `.o2r` files are `.zip` compatible files" ([LUS README](https://github.com/HarbourMasters/libultraship/blob/main/README.md)).
- SoH keeps the console's **Yaz0** decompressor: `soh/src/boot/yaz0.c` plus use in `soh/src/boot/z_std_dma.c`, with declarations in `include/functions.h` and `include/z64.h` ([SoH src/boot/yaz0.c](https://github.com/HarbourMasters/Shipwright/blob/develop/soh/src/boot/yaz0.c)). This is the decompilation's own Yaz0 routine, kept compiled.
- SoH re-serialises audio assets through dedicated resource importers/types: `soh/soh/resource/importer/AudioSampleFactory.cpp`, `AudioSequenceFactory.cpp`, `AudioSoundFontFactory.cpp`, and `resource/type/AudioSample.cpp`, `AudioSequence.cpp`, `AudioSoundFont.cpp` ([SoH resource listing](https://github.com/HarbourMasters/Shipwright/tree/develop/soh/soh/resource/importer)). The game still loads/plays them via the decompiled `src/code/audio_load.c`, `audio_playback.c`, `audio_seqplayer.c` ([SoH src/code listing](https://github.com/HarbourMasters/Shipwright/tree/develop/soh/src/code)).
- Resource-from-ROM→archive tooling is ZAPD (`ZAPDTR`) plus `OTRExporter`, run by `extract_assets.py` at first launch ([SoH BUILDING.md](https://github.com/HarbourMasters/Shipwright/blob/develop/BUILDING.md); the-harbour docs: "When you first launch Ship of Harkinian, it will extract the assets from your ROM and create an oot.o2r archive with all assets separated into individual files in a special binary format" — [the-harbour O2R format doc, from search-indexed copy](https://github.com/garrettjoecox/the-harbour/blob/main/docs/ship-of-harkinian/o2r-format/index.md)).
- sm64ex's sound assets are likewise extracted and compiled in: samples are custom-ADPCM AIFF, banks and `.m64` sequences are processed by the build ([n64decomp/sm64 sound/README.md](https://github.com/n64decomp/sm64/blob/master/sound/README.md); [sm64ex sound/](https://github.com/sm64pc/sm64ex/tree/nightly/sound)).

### Inferences
- Cartridge-layout fidelity is **not** maintained at runtime in either port because assets are moved to a host representation (compiled-in for SM64; repacked archives for SoH). Compatibility is instead maintained at *extraction* time (parsers must read the original ROM/asset formats correctly), which matches the LUS/OTR design goal of mod-friendly, individually replaceable resources.
- Keeping `yaz0.c` as source (SoH) means the console compression format is preserved and re-runnable even though assets live in archives; sm64ex has no need for it because its sequence/sample formats are decoded at build time.

### Gaps
- I could not retrieve a **live** copy of the-harbour O2R format doc (the URL 404s on fetch and the file is absent from the repo's current `main` tree); its content here is quoted from a search-indexed copy. A verified live statement of O2R's binary layout is therefore a gap.
- I did not inspect `ZAPDTR`/`OTRExporter` to confirm exactly which ROM assets are stored verbatim vs. re-encoded.

## Q5: What changed for a host filesystem, and what was kept?

### Takeaway
Both ports introduce a small **virtual filesystem layer**: a read-search path over mounts/packs plus a distinct **writable user directory**. sm64ex exposes `src/pc/fs/` with mountable directory and zip packs; SoH inherits LUS's `ArchiveManager` (Folder/Otr/O2r archives) and uses `std::filesystem` directly for saves. What is **kept** is the game's address-space assumptions in code (via `osVirtualToPhysical`) and, for sm64ex, the exact on-disk save byte layout / EEPROM 8-byte addressing.

### Cited Findings
- sm64ex `src/pc/fs/fs.h` defines a pack abstraction (`fs_packtype_t` with `open/read/seek/tell/size/eof/close`), a mount API (`fs_mount`/`fs_unmount`), a search path (`fs_init(rodirs, gamedir, userdir)`), a separate write path (`fs_writepath`, `fs_get_write_path`, `fs_convert_path`), and defaults `FS_BASEDIR "res"`, `FS_SOUNDDIR "sound"`, with dir and zip pack types ([sm64ex src/pc/fs/fs.h](https://github.com/sm64pc/sm64ex/blob/nightly/src/pc/fs/fs.h); implementations `fs_packtype_dir.c`, `fs_packtype_zip.c`, `dirtree.c` — [listing](https://github.com/sm64pc/sm64ex/tree/nightly/src/pc/fs)).
- sm64ex saves were moved onto that FS: the EEPROM shim opens `SAVE_FILENAME` through `fs_open(...)` and writes through `fs_get_write_path(SAVE_FILENAME)` (and, for the web target, `localStorage`), i.e. host-relative virtual paths rather than cartridge addresses ([sm64ex src/pc/ultra_reimplementation.c](https://github.com/sm64pc/sm64ex/blob/nightly/src/pc/ultra_reimplementation.c)).
- SoH/LUS archive layer: `ArchiveManager` with `FolderArchive`, `OtrArchive`, `O2rArchive`, plus `ResourceLoader`/`ResourceManager`, and bridges (`resourcebridge.cpp`) that let game C code request resources by ID ([LUS resource headers](https://github.com/HarbourMasters/libultraship/tree/main/include/ship/resource); [LUS src/ship/resource](https://github.com/HarbourMasters/libultraship/tree/main/src/ship/resource)). `.o2r`/`.otr` packs can be dropped in a `mods` folder and automatically override data ([LUS README](https://github.com/HarbourMasters/libultraship/blob/main/README.md)).
- SoH writes saves with a host filesystem path and JSON: `SaveManager` builds `Ship::Context::GetPathRelativeToAppDirectory("Save")`, creates the directory if missing, uses `WriteFileSafely`, and migrates legacy `oot_save.sav` to `oot_save.bak` after conversion ([SoH soh/SaveManager.cpp](https://github.com/HarbourMasters/Shipwright/blob/develop/soh/soh/SaveManager.cpp)); corrupt saves are renamed with a Unix-timestamp suffix as a backup ([same file](https://github.com/HarbourMasters/Shipwright/blob/develop/soh/soh/SaveManager.cpp)).
- What was kept: physical/virtual address conversion still exists so N64 pointers work (`osVirtualToPhysical` in sm64ex; LUS `osCartRomInit`/`osEPiStartDma` in SoH) ([sm64ex ultra_reimplementation.c](https://github.com/sm64pc/sm64ex/blob/nightly/src/pc/ultra_reimplementation.c); [LUS os.cpp](https://github.com/HarbourMasters/libultraship/blob/main/src/libultraship/libultra/os.cpp)).
- The console EEPROM **8-byte address granularity** is preserved in both the game code (`offset = baseofs >> 3`) and the sm64ex shim (`content + address * 8`) ([sm64ex src/game/save_file.c](https://github.com/sm64pc/sm64ex/blob/nightly/src/game/save_file.c); [ultra_reimplementation.c](https://github.com/sm64pc/sm64ex/blob/nightly/src/pc/ultra_reimplementation.c)).

### Inferences
- The host-FS design is a **read-only search path + one writable user dir**, which is the minimum needed to keep decompiled code's asset lookups working while making data moddable; it does not try to reproduce cartridge ROM layout at runtime.
- Because sm64ex writes the console EEPROM image (with shifts), its save-on-disk behaviour is deliberately *not* "native-readable"; it trades host ergonomics (unless `TEXTSAVES`) for console fidelity. SoH trades the opposite way (JSON ergonomics) but retains an import/byte-offset bridge.

### Gaps
- I did not verify the exact string value of `SAVE_FILENAME` in sm64ex (referenced but not captured).

## Q6: Is there any documented rule about keeping data formats identical to the console's (for emulator/hardware interop)?

### Takeaway
There is no single port-wide "keep everything byte-identical" charter, but there are **explicit fidelity rules** in three places: (1) LUS's/O2R tooling requirement that exported resource files match the binary format exactly; (2) the projects' dependency on the **decompilation's byte-matching ROM requirement**, which forces struct/layout fidelity; and (3) concrete interop features — sm64ex's big-endian EEPROM image and SoH's N64-SRAM import, both explicitly tied to console/emulator save formats.

### Cited Findings
- Resource-format exactness: the SoH O2R format documentation states that when creating resource tooling it is important that the format a tool exports "matches this binary format exactly" ([the-harbour O2R format doc — search-indexed copy](https://github.com/garrettjoecox/the-harbour/blob/main/docs/ship-of-harkinian/o2r-format/index.md)). The archive container choice reinforces interoperability with standard tools: `.otr` is MPQ-compatible, `.o2r` is zip-compatible ([LUS README](https://github.com/HarbourMasters/libultraship/blob/main/README.md)).
- The decompilation projects must produce **byte-identical ROMs** against published SHA-1 sums (`sm64.us.sha1`, `sm64.jp.sha1`, `sm64.eu.sha1` in the repo), which constrains all data-structure layouts, padding and endianness to match the console ([n64decomp/sm64 repo](https://github.com/n64decomp/sm64)). SoH is "dependant on the source code provided by the OOT decompilation project," i.e. the same constraint ([SoH README](https://github.com/HarbourMasters/Shipwright/blob/develop/README.md)).
- Explicit console/save interoperability: sm64ex writes the EEPROM image big-endian on LE hosts and detects/swaps big-endian console saves ([sm64ex src/game/save_file.c](https://github.com/sm64pc/sm64ex/blob/nightly/src/game/save_file.c)); the SM64 EEPROM format is separately documented for save editors ([bryc/sm64eep](https://github.com/bryc/sm64eep)). SoH parses the exact N64 SRAM header/slot layout when importing `oot_save.sav` ([SoH soh/SaveManager.cpp](https://github.com/HarbourMasters/Shipwright/blob/develop/soh/soh/SaveManager.cpp)); a third-party tool documents bidirectional conversion between SoH/PC saves and N64 emulator (`.sra`, little-endian) and console (big-endian) formats ([ZeldaSaveTool README](https://github.com/xoascf/ZeldaSaveTool)).
- Verification point for tooling: SoH's setup validates the ROM hash before extraction ("Incompatible ROM hash" if wrong), so assets are always derived from a known console image ([soh BUILDING/README flow](https://github.com/HarbourMasters/Shipwright/blob/develop/BUILDING.md)).

### Inferences
- The de-facto rule is **"match the console where it is observable, abstract where it is not."** Observable console artifacts (ROM bytes → struct layouts; save images → magic/checksum/endianness; resource binaries → exact layouts) are kept identical; non-observable hardware (VI, RSP, scheduler) is freely reimplemented. This is the pattern an eidos port should mirror for the DS's FS_/OS_/MI_ surface and save structs.
- Byte-exactness in these ports is largely *inherited for free* from the decompilation's matching requirement, not enforced by an explicit port policy document.

### Gaps
- **No live primary source** was found stating a blanket "data structures must stay byte-identical for emulator/hardware interop" rule for the ports; the closest explicit statement is the O2R tooling requirement (sourced only from a search-indexed, since-removed doc) plus the decompilation matching requirement.
- I found no port documentation that discusses N64 audio-microcode or save-format fidelity as an explicit *design goal*; the fidelity is inferable from code but not stated in prose, apart from the OTR/O2R archive documentation.
