# How the SM64 port / sm64ex and Ship of Harkinian (libultraship) execute N64 graphics hardware on a PC

Scope note: This report covers (a) the SM64 PC port lineage — `sm64-port` / `sm64ex`, whose renderer is the Fast3D interpreter in `src/pc/gfx/gfx_pc.c`, and (b) Ship of Harkinian (SoH) via **libultraship (LUS)**, whose renderer is `src/fast/interpreter.cpp`. Both descend from Emill's `n64-fast3d-engine`. Every claim below is sourced; where I could not verify something I say so explicitly. Note on citations: the raw files I read are large single files; I cite the canonical GitHub `blob`/`raw` URLs plus the specific function/struct/line-region names so the reader can locate them.

---

## Q1. What is a GBI display list, and how do the ports execute it on a PC? (Does the port interpret the command stream, or replace drawing calls at a higher level?)

### Takeaway
A display list is a runtime-built array of fixed 8-byte command words handed to the RSP; the "GBI" is the macro/opcode interface that game C code uses to build it. Both ports **interpret the original command stream** at runtime — they decode each 8-byte opcode and emulate the RSP/RDP state machine and primitive assembly on the CPU/GPU. Neither replaces drawing at a high level; the game's own display-list-building code runs as written and produces real GBI words that the interpreter consumes.

### Cited Findings
- "A display list is simply a list of commands indicating to the RSP what should be rendered on the screen every frame." A command "corresponds to an element of type `Gfx`, which has a size of 64 bits (8 bytes)"; the first byte is always the command type; `G_ENDDL` (byte `0xDF`) terminates a list; lists have no start marker. Static commands come from `gsSP*`/`gsDP*` macros, dynamic ones from `gSP*`/`gDP*` macros with a post-incremented pointer — [HackMD, "N64 Gfx Decompilation (F3DEX & S2DEX)"](https://hackmd.io/@Roman971/Hk01jRxRr).
- "You can think of a display list as an array of 64-bit words (8 bytes) where each element of the array is a command that the RSP will use to render the frame… The graphics programmer controls the RSP from main game code using the GBI." — [RetroReversing, N64 RSP](https://www.retroreversing.com/n64rsp).
- Hack64's SM64 opcode reference documents that Fast3D commands "are all 8 bytes long" and enumerates the opcodes (e.g. `G_MTX`=0x01, `G_VTX`=0x04, `G_DL`=0x06, `G_TRI1`=0xBF in the original F3D encoding) — [Hack64, Fast3D Display List Commands](https://hack64.net/wiki/doku.php?id=super_mario_64:fast3d_display_list_commands).
- **sm64ex executes the command stream** via `gfx_run(Gfx *commands)` → `gfx_run_dl(Gfx* cmd)`, which loops `opcode = cmd->words.w0 >> 24;` and `switch (opcode)` over `G_MTX`, `G_VTX`, `G_TRI1`, `G_TEXRECT`, `G_SETCOMBINE`, `G_SETTILE`, `G_SETTIMG`, etc. — [sm64ex `src/pc/gfx/gfx_pc.c`, functions `gfx_run` / `gfx_run_dl`](https://github.com/sm64pc/sm64ex/blob/master/src/pc/gfx/gfx_pc.c).
- **libultraship executes the command stream** via `Interpreter::Run(Gfx* commands, ...)` dispatching through `gfx_step()`, which reads `int8_t opcode = (int8_t)(cmd->words.w0 >> 24);` and looks the opcode up in handler tables (`otrHandlers`, `rdpHandlers`, `ucode_handlers[...]`) — [LUS `src/fast/interpreter.cpp`, `gfx_step`](https://github.com/HarbourMasters/libultraship/blob/main/src/fast/interpreter.cpp), declared as `void Run(Gfx* commands, const std::unordered_map<Mtx*, MtxF>& mtx_replacements);` — [LUS `include/fast/interpreter.h`](https://github.com/HarbourMasters/libultraship/blob/main/include/fast/interpreter.h).
- LUS describes its own renderer as "The Fast3D Renderer. Interprets N64 display lists as commands for modern GPUs. Supports OpenGL, Direct3D 11, and Metal backends." — [LUS Porting Guide, directory table](https://libultraship.com/PORTING).
- The command bytes are produced by the game's own code: LUS ships `gbi.h` with the `gSP*`/`gDP*`/`gsSP*`/`gsDP*` macro definitions (e.g. `GPACK_RGBA5551`, `G_MTX_PUSH`, `G_SETCOMBINE` mux constants) — [LUS `include/libultraship/libultra/gbi.h`](https://github.com/HarbourMasters/libultraship/blob/main/include/libultraship/libultra/gbi.h); the interpreter's own opcode set lives in [LUS `include/fast/lus_gbi.h`](https://github.com/HarbourMasters/libultraship/blob/main/include/fast/lus_gbi.h) (which `#include`s `f3dex.h` and `f3dex2.h`).
- Each interpreter decodes bit-fields out of the 64-bit word, e.g. sm64ex `G_SETCOMBINE` splits `C0(20,4), C1(28,4), C0(15,5), C1(15,3)` into a color-combiner id — [sm64ex `gfx_pc.c`, `case G_SETCOMBINE`](https://github.com/sm64pc/sm64ex/blob/master/src/pc/gfx/gfx_pc.c).
- Emill's `n64-fast3d-engine` is the upstream of this architecture: "Implementation of a Fast3D renderer for games built originally for the Nintendo 64 platform." — [Emill/n64-fast3d-engine](https://github.com/Emill/n64-fast3d-engine). sm64ex advertises "the original GL2.1, D3D11 and D3D12 renderers from Emill's n64-fast3d-engine." — [sm64pc/sm64ex README](https://github.com/sm64pc/sm64ex).

### Inferences
- Because both ports consume raw GBI words, **any display list the game builds at runtime is executed** — including dynamically generated lists (animation matrices, per-frame transformed geometry). This is a fundamentally different shape from a "port reimplements the draw call" design.
- The interpreter is effectively a CPU reimplementation of the RSP microcode's per-command behavior plus a CPU/GPU reimplementation of the RDP pipeline. The RSP's fixed-function transform/lighting work is done in float on the CPU (`gfx_sp_matrix`, `gfx_sp_vertex`), then triangles are batched to the GPU (`gfx_sp_tri1` appends to a VBO and flushes).

### Gaps
- Could not find an authored, narrative design doc for the libultraship Fast3D interpreter beyond the short `src/fast/README.md`; there is no long-form "how the interpreter works" article. The behavioural claims above are read directly from the source.

## Q2. How faithful is the interpretation? Which GBI variants are supported? What is the failure mode for an unsupported command?

### Takeaway
Faithfulness is "high enough to run commercial games unmodified" but not cycle-exact: it is a **behavioural RSP/RDP emulation**, with the RDP color combiner translated into generated GPU shaders and RSP transform/lighting reimplemented in float. libultraship selects one of six microcode profiles (`f3d, f3db, f3dex, f3dexb, f3dex2, s2dex`; default `f3dex2`) and can switch at runtime via `G_LOAD_UCODE`. Unsupported commands are **logged as critical and skipped**, not halted.

### Cited Findings
- libultraship's supported µcodes: `UcodeHandlers ucode_handler_index = ucode_f3dex2;` with handler tables `ucode_handlers = { &f3dHandlers /*f3db*/, &f3dHandlers /*f3d*/, &f3dexHandlers /*f3dex*/, &f3dexHandlers /*f3dexb*/, &f3dex2Handlers /*f3dex2*/, &s2dexHandlers /*s2dex*/ }` — [LUS `src/fast/interpreter.cpp`](https://github.com/HarbourMasters/libultraship/blob/main/src/fast/interpreter.cpp).
- Runtime µcode switch: `if (opcode == F3DEX2_G_LOAD_UCODE) { gfx_set_ucode_handler((UcodeHandlers)(cmd->words.w0 & 0xFFFFFF)); …}` — [LUS `interpreter.cpp`, `gfx_step`](https://github.com/HarbourMasters/libultraship/blob/main/src/fast/interpreter.cpp).
- The F3DEX2 handler table contains: `G_NOOP, G_SPNOOP, G_CULLDL, G_MTX, G_POPMTX, G_MOVEMEM, G_MOVEWORD, G_TEXTURE, G_VTX, G_MODIFYVTX, G_DL, G_ENDDL, G_GEOMETRYMODE, G_TRI1, G_TRI2, G_QUAD, G_SETOTHERMODE_L, G_SETOTHERMODE_H` — [LUS `interpreter.cpp`, `f3dex2Handlers`](https://github.com/HarbourMasters/libultraship/blob/main/src/fast/interpreter.cpp).
- LUS's build-level µcode selection: "`GBI_UCODE` | `F3DEX_GBI_2` (default) | Graphics microcode variant (`F3DEX_GBI_2`, `F3DEX_GBI`, `F3DLP_GBI`)" — [LUS Porting Guide, build options](https://libultraship.com/PORTING). The header itself branch-defines the entire opcode set on these three macros — [LUS `gbi.h`](https://github.com/HarbourMasters/libultraship/blob/main/include/libultraship/libultra/gbi.h).
- SoH is built on Ocarina of Time's decompilation; OOT/MM use **F3DZEX2**, which "is a variant of the F3DEX2 … containing a very similar (if not identical) binary interface" — [CloudModding OoT Wiki, F3DZEX2](https://wiki.cloudmodding.com/oot/F3DZEX2). (LUS's `f3dex2` handler is the profile used for OOT-family games; see Gaps for the exact `gfx_set_target_ucode` call site.)
- S2DEX is partially supported: `s2dexHandlers` implements `G_BG_COPY`, `G_BG_1CYC`, `G_OBJ_RECTANGLE`, and `G_DL`/`G_ENDDL`; `G_OBJ_RENDERMODE` and `G_OBJ_RECTANGLE_R` are routed to `gfx_stubbed_command_handler`; there is an in-source note: "These S2DEX commands have different opcode numbers on F3DEX2 vs other ucodes. More research needs to be done…" — [LUS `interpreter.cpp`, `s2dexHandlers`](https://github.com/HarbourMasters/libultraship/blob/main/src/fast/interpreter.cpp).
- **Failure mode (libultraship):** unknown opcode → `SPDLOG_CRITICAL("Unhandled OP code: 0x{:X}, for loaded ucode: {}", …)`, then `++cmd;` and continue — i.e. log-and-skip, no abort. Same log exists in `GfxGetOpcodeName` — [LUS `interpreter.cpp`](https://github.com/HarbourMasters/libultraship/blob/main/src/fast/interpreter.cpp).
- **Failure mode (sm64ex):** the `switch (opcode)` in `gfx_run_dl` has no `default:` case, so unknown opcodes are silently ignored and iteration proceeds to `++cmd` — [sm64ex `gfx_pc.c`, `gfx_run_dl`](https://github.com/sm64pc/sm64ex/blob/master/src/pc/gfx/gfx_pc.c).
- Explicit no-op handlers exist for commands that are semantically "sync": `mRdpLOADSYNC`, `mRdpPIPESYNC`, `mRdpTILESYNC`, `mRdpFULLSYNC`, and `mRdpHALF_1` are all bound to `gfx_stubbed_command_handler` — [LUS `interpreter.cpp`, `rdpHandlers`/`f3dexHandlers`](https://github.com/HarbourMasters/libultraship/blob/main/src/fast/interpreter.cpp).
- **sm64ex GBI variants:** `gfx_run_dl` branches on `#ifdef F3DEX_GBI_2`, `#elif defined(F3DEX_GBI) || defined(F3DLP_GBI)`, `#else` — decoding `G_VTX`/`G_TRI1`/`G_MTX`/`G_MOVEMEM`/`G_MOVEWORD` differently, including the original Fast3D `G_TRI1(C1(16,8)/10, …)` and `G_POPMTX` count semantics — [sm64ex `gfx_pc.c`, `gfx_run_dl`](https://github.com/sm64pc/sm64ex/blob/master/src/pc/gfx/gfx_pc.c). SM64's µcode ("Fast3D") is documented as the microcode SM64 uses — [mountainflaw, Fast3D Displaylist Macros](https://mountainflaw.github.io/assets/page/dl_macros.html).
- The RSP transform path is explicitly reimplemented: `gfx_sp_matrix` concatenates `P_matrix`/modelview stacks (with a `#if 0` note "Original code when fixed point matrices were used" and the live path using `memcpy(matrix, addr, sizeof(matrix))` — i.e. float matrices via `GBI_FLOATS`), and `gfx_sp_vertex` performs the MP-matrix multiply and light/intensity computation — [sm64ex `gfx_pc.c`](https://github.com/sm64pc/sm64ex/blob/master/src/pc/gfx/gfx_pc.c); the `src/fast/README.md` advises "please change the Vtx and Mtx structures to use floats instead of fixed point arithmetic (`GBI_FLOATS`)." — [LUS `src/fast/README.md`](https://github.com/HarbourMasters/libultraship/blob/main/src/fast/README.md).
- The RDP color combiner is compiled into shaders: `GenerateCC` (LUS) / `gfx_generate_cc` (sm64ex) turn the `G_SETCOMBINE` mux fields into a `ColorCombinerKey`/shader id, and lighting/coverage are handled as shader options (`SHADER_OPT_ALPHA`, `SHADER_OPT_FOG`, `SHADER_OPT_TEXTURE_EDGE`, `SHADER_OPT_NOISE`, `SHADER_OPT(_2CYC)`) — [LUS `interpreter.h`, `ShaderOpts`](https://github.com/HarbourMasters/libultraship/blob/main/include/fast/interpreter.h); [sm64ex `gfx_pc.c`, `gfx_generate_cc` and `gfx_sp_tri1` options](https://github.com/sm64pc/sm64ex/blob/master/src/pc/gfx/gfx_pc.c).
- Fidelity limitations visible in source: LOD is a crude approximation (`float distance_frac = (v1->w - 3000.0f) / 3000.0f;` in sm64ex's `CC_LOD` case); coverage/anti-alias bits (`AA_EN`, `CVG_*`) are not modelled; `G_CCMUX_LOD_FRACTION`/some muxes fall to `default:` → `fprintf(stderr, "Unsupported ccmux: %d\n", …)` in LUS — [sm64ex `gfx_pc.c`](https://github.com/sm64pc/sm64ex/blob/master/src/pc/gfx/gfx_pc.c); [LUS `interpreter.cpp`, `GenerateCC`](https://github.com/HarbourMasters/libultraship/blob/main/src/fast/interpreter.cpp).

### Inferences
- "Faithful" here means *original command stream is authoritative and executed* — not *pixel-identical to the RDP*. Expect approximation in LOD/mip blending, coverage, dithering, YUV chroma-key, and the fixed-function precision of RSP transform/lighting (float vs the N64's fixed-point).
- The unsupported-command behaviour (log-and-skip) is a deliberate "run the 99% of the stream that is understood" policy. The practical risk is silent visual glitches on games whose custom µcode emits opcodes LUS doesn't know, which matches the Porting Guide's warning that "Custom UCodes (e.g., specific Rareware implementations) may need manual implementation or adjustments in the renderer." — [LUS Porting Guide](https://libultraship.com/PORTING).

### Gaps
- I did not directly read the SoH/`Shipwright` call site that invokes `gfx_set_target_ucode`/`ucode_f3dex2` for OOT; I confirmed LUS's default is `ucode_f3dex2` and that F3DZEX2 ≈ F3DEX2 at the binary-interface level, but the explicit per-game selection line was not fetched.
- I could not find a formal "supported / unsupported command" matrix document; the handler tables in `interpreter.cpp` are the authoritative list.
- `G_BRANCH_Z` (0x04) is absent from LUS's `f3dex2Handlers` table while a custom `OTR_G_BRANCH_Z_OTR` (0x35) datapath exists (`gfx_branch_z_otr_handler_f3dex2`, and `G_EX_ALWAYS_EXECUTE_BRANCH`), which suggests the port replaces OOT's branch-Z command at the source/asset level. I did not find a primary doc confirming the source replacement, so I flag this as an inference only.

## Q3. How is hardware register state modelled? (N64 MMIO at 0xA4xxxxxx, VI registers, RDP command registers — is there a register file with write hooks as on a real machine?)

### Takeaway
**No memory-mapped register file, and no MMIO write hooks.** This is the crucial architectural point: the graphics "registers" a game touches are not MMIO at all on the N64 — the `gSP*`/`gDP*` macros write GBI commands into an ordinary RAM `Gfx` buffer, and the RSP microcode consumes that buffer. So there is nothing at `0xA4xxxxxx` to emulate for rendering. The interpreter instead keeps two C++ structs, `RSP` and `RDP`, as a *behavioural state model* updated by the command handlers. The VI (`osVi*`) functions are reimplemented as **empty no-op stubs**; presentation is owned by the window/back-end, not by a modelled VI register set.

### Cited Findings
- libultraship models hardware state as plain structs: `struct RSP { float modelview_matrix_stack[11][4][4]; … float P_matrix[4][4]; F3DLight_t current_lights[MAX_LIGHTS+1]; uint32_t geometry_mode; int16_t fog_mul, fog_offset; struct { uint16_t s, t; } texture_scaling_factor; struct LoadedVertex loaded_vertices[MAX_VERTICES+4]; };` and `struct RDP { const uint8_t* palettes[2]; … texture_to_load; loaded_texture[2]; texture_tile[8]; uint32_t other_mode_l, other_mode_h; uint64_t combine_mode; … RGBA env_color, prim_color, fog_color, blend_color, fill_color; XYWidthHeight viewport, scissor; void* z_buf_address; void* color_image_address; };` — [LUS `include/fast/interpreter.h`](https://github.com/HarbourMasters/libultraship/blob/main/include/fast/interpreter.h). They are owned by the `Interpreter` object (`RSP* mRsp; RDP* mRdp;`) and updated by the `GfxSp*`/`GfxDp*` handler methods.
- sm64ex has the same shape, smaller: `static struct RSP { … } rsp;` and `static struct RDP { … } rdp;`, with fields mirroring the same hardware state (matrix stacks, lights, `geometry_mode`, `fog_mul/offset`, `other_mode_l/h`, `combine_mode`, `env_color/prim_color/fog_color/fill_color`, `viewport`, `scissor`, `z_buf_address`, `color_image_address`) — [sm64ex `gfx_pc.c`](https://github.com/sm64pc/sm64ex/blob/master/src/pc/gfx/gfx_pc.c).
- The GBI macros that game code calls are **RAM writes to a `Gfx` buffer**, not MMIO — they take a `gdl` pointer, e.g. `gDPPipeSync(displayListPointer++);` and `gSPMatrix(ptr++, …, …)` write 8-byte words into a C array — [HackMD, "N64 Gfx Decompilation", dynamic-macro examples](https://hackmd.io/@Roman971/Hk01jRxRr); the `Gfx`/`F3DGfx` union is defined in [LUS `lus_gbi.h`→`f3dex.h`/`f3dex2.h` chain](https://github.com/HarbourMasters/libultraship/blob/main/include/fast/lus_gbi.h) and in `gbi.h`.
- Segment/address translation is emulated from GBI state, not a memory map: `#define SEG_ADDR(seg, addr) (addr | (seg << 24) | 1)` (LUS) / `static inline void *seg_addr(uintptr_t w1) { return (void*) w1; }` (sm64ex), fed by `G_MW_SEGMENT` and `mSegmentPointers[16]` — [LUS `interpreter.cpp`](https://github.com/HarbourMasters/libultraship/blob/main/src/fast/interpreter.cpp); [sm64ex `gfx_pc.c`](https://github.com/sm64pc/sm64ex/blob/master/src/pc/gfx/gfx_pc.c).
- **VI is not modelled — the `osVi*` functions are empty stubs:** in `src/libultraship/libultra/os_vi.cpp`, `osViSwapBuffer`, `osViSetSpecialFeatures`, `osViSetMode`, `osViBlack`, `osViSetXScale`, `osViSetYScale` have empty bodies; `osViGetNextFramebuffer`/`osViGetCurrentFramebuffer` return `nullptr`; `osCreateViManager` merely installs an SDL timer (`SDL_AddTimer(16, &__lusViCallback, NULL)`) that posts an `OS_EVENT_VI` message, and `osViSetEvent` records the queue/message — [LUS `src/libultraship/libultra/os_vi.cpp`](https://github.com/HarbourMasters/libultraship/blob/main/src/libultraship/libultra/os_vi.cpp).
- Other OS subsystems are reimplemented as libultra functions rather than MMIO: the repo contains `os.cpp`, `os_cache.cpp`, `os_eeprom.cpp`, `os_mesg.cpp`, `os_pi.cpp`, `os_time.cpp`, `os_vi.cpp`, `os_vm.cpp`, `AudioDmaRegistry.cpp` — [LUS `src/libultraship/libultra/`](https://github.com/HarbourMasters/libultraship/tree/main/src/libultraship/libultra).
- libultraship frames itself as replacing the SDK, not the silicon: LUS "provide[s] reimplementations of libultra (n64 sdk) functions that run on modern hardware." — [LUS README](https://github.com/HarbourMasters/libultraship/blob/main/README.md). Harbour Masters: "LibUltraShip (LUS) is our modern recreation of the Nintendo 64 SDK, known as LibUltra. It provides the foundation for all our ports, handling graphics, audio, input, and core game systems." — [Harbour Masters About](https://www.harbourmasters.org/about).
- The RDP "command registers" (`other_mode`, combine mode, tile descriptors, env/prim/fog colors, viewport, scissor) are fields on `RDP`/`RSP` and are shadowed for GPU state diffing: LUS keeps a `RenderingState { … depth_test_and_mask; decal_mode; alpha_blend; viewport, scissor; ShaderProgram* mShaderProgram; TextureCacheNode* mTextures[...]; }` and only issues GPU calls when a field differs (e.g. `if (rdp.viewport_or_scissor_changed) { … gfx_rapi->set_viewport(...) }`) — [LUS `interpreter.h`, `RenderingState`](https://github.com/HarbourMasters/libultraship/blob/main/include/fast/interpreter.h); sm64ex's `struct RenderingState` does the same — [sm64ex `gfx_pc.c`, `gfx_sp_tri1`](https://github.com/sm64pc/sm64ex/blob/master/src/pc/gfx/gfx_pc.c).

### Inferences
- For a project that compiles matched decompilation unchanged (the eidos case): the N64 analogue shows that the *only* state you need to model is the state the game's own C code reads back. N64 graphics give no readback path, so the ports never had to expose a register file — the GBI command buffer is write-only from the game's perspective. If eidos's Pokemon Black code reads hardware registers back (e.g. polls DISPCNT/VCOUNT/DISPSTAT), a write-hook register file **would** be needed; the N64 ports are not a precedent for that because they never needed readback. This is the key asymmetry to note.
- The VI stubs imply the ports deliberately drop VI timing/scanout semantics and let the window manager + backend own presentation and vsync; the game still receives a VI event at ~60 Hz via the SDL timer so its message loop progresses.

### Gaps
- I found **no** register-file or MMIO write-hook abstraction anywhere in either port — searches of `interpreter.cpp`/`interpreter.h`/`os_vi.cpp` returned none. So I can state the absence with reasonable confidence for the graphics path, but I did not exhaustively scan every `os_*.cpp` for MMIO (e.g. PI/SI/AI register handling); `os_pi.cpp` and `AudioDmaRegistry.cpp` exist and were not read in full.
- No source evidence of the N64's `0xA4xxxxxx`/`0xA3xxxxxx` physical MMIO ranges being emulated; the ports do not appear to map those addresses at all.

## Q4. How much of the original rendering code runs unchanged? Does the game's own display-list generation code execute as written?

### Takeaway
The *display-list generation logic* runs essentially unchanged, because the ports supply drop-in `gbi.h` macros and libultra function reimplementations and the game is recompiled against them (LUS calls itself a "compile-time WINE"). What is **not** byte-identical: asset payloads and some pointer addresses are re-authored/relocated (OTR/O2R + Torch), and a handful of commands are replaced with custom "OTR" opcodes. So: the C *control flow and macro calls* run as written; the *asset bytes and certain DL entries* are transformed.

### Cited Findings
- "It is not a recompilation tool; rather, it allows developers to build a game's original source code (derived from decompilation) on modern hardware by providing a **header-compatible wrapper around modern reimplementations of N64 SDK functions**. In essence, LUS acts as **'compile-time WINE'** for the N64." Porting step 2 is literally "Header Replacement: Replace N64 SDK includes (e.g. `#include <ultra64.h>`) in the source code with LUS includes: `#include <libultraship/libultraship.h>`." — [LUS Porting Guide](https://libultraship.com/PORTING).
- "Ship of Harkinian (SOH) is built atop a custom library dubbed libultraship (LUS). … LUS is designed to mimic the functionality of libultra on modern hardware. In addition, we are dependent on the source code provided by the OOT decompilation project." — [HarbourMasters/Shipwright README](https://github.com/HarbourMasters/Shipwright).
- The GBI macros are real C that build the same `Gfx` structures the game expects, so calls like `gDPSetEnvColor`, `gSPMatrix`, `gSPSetGeometryMode` compile and run — [LUS `gbi.h`](https://github.com/HarbourMasters/libultraship/blob/main/include/libultraship/libultra/gbi.h); [HackMD decompilation guide](https://hackmd.io/@Roman971/Hk01jRxRr).
- **Not fully unchanged — custom opcodes are injected:** `lus_gbi.h` defines a large block of `// CUSTOM OTR COMMANDS` and `// GFX Effects` opcodes, e.g. `OTR_G_SETTIMG_OTR_HASH (0x20)`, `OTR_G_DL_OTR_FILEPATH (0x27)`, `OTR_G_MTX_OTR (0x36)`, `OTR_G_BRANCH_Z_OTR (0x35)`, `OTR_G_TEXRECT_WIDE (0x37)`, `OTR_G_FILLWIDERECT (0x38)`, `OTR_G_COPYFB (0x3b)`, `OTR_G_READFB (0x3e)`, `RDP_G_VTX_WIDE (0x48)`, `RDP_G_TRI1_WIDE (0x49)` — [LUS `include/fast/lus_gbi.h`](https://github.com/HarbourMasters/libultraship/blob/main/include/fast/lus_gbi.h).
- These custom opcodes are what the interpreter receives at runtime; `gfx_step` checks `otrHandlers` **before** the µcode/RDP tables — [LUS `gfx_step`](https://github.com/HarbourMasters/libultraship/blob/main/src/fast/interpreter.cpp). Handler names like `gfx_set_timg_otr_hash_handler_custom`, `gfx_dl_otr_hash_handler_custom`, `gfx_mtx_otr_handler_custom`, `gfx_tex_rect_wide_handler_custom` confirm they are first-class interpreter commands — [LUS `interpreter.cpp`, `otrHandlers`](https://github.com/HarbourMasters/libultraship/blob/main/src/fast/interpreter.cpp).
- Asset/PIE re-authoring: the Porting Guide's "Phase 3: Assets (The Fork in the Road)" states that the recommended path converts assets with **Torch**, "an external tool designed to swap C files to path references and regenerate headers automatically," producing `.o2r`/`.otr` archives; the alternative is to "manually 'massage' the assets to handle endianness … and bit-width differences between N64 and PC." — [LUS Porting Guide](https://libultraship.com/PORTING); [LUS README on OTR/O2R](https://github.com/HarbourMasters/libultraship/blob/main/README.md).
- SoH extracts all "copyrighted assets … from the ROM and reformat[s them] as a `.o2r` archive file which the code uses." — [HarbourMasters/Shipwright README](https://github.com/HarbourMasters/Shipwright).

### Inferences
- The phrase "compiles the decompilation's matched C unchanged" applies to N64 ports *at the level of render logic*: the game's `gSP*`/`gDP*` call sites are the same C, but the macro definitions and the data pointers they embed are port-provided. For eidos this maps to: the DS game's VRAM/OAM/DISPCNT *writes* in matched C can stay unchanged **if** the port supplies the same header-level primitives (a register-write macro/volatile-address layer) that route to the port's register file — exactly as LUS supplies `gbi.h` macros route to the interpreter.
- Dynamic DL generation (e.g. OOT building DLs during gameplay) is preserved by construction, since the identical C runs against drop-in macros. This is the strongest argument for the interpreter approach over asset conversion.

### Gaps
- I did not enumerate exactly which OOT source files are patched to emit the custom OTR opcodes (e.g. where `gfx_set_target_ucode`/`G_TEXRECT_WIDE` are emitted). The existence and semantics of the custom opcodes are confirmed; the source-diff of the game side is not.

## Q5. How do they handle resolution scaling, widescreen, framebuffer formats and texture formats?

### Takeaway
Resolution scaling is **decoupled from the game's assumption of a 320×240 N64 framebuffer**. Both ports keep a "native" 320×240 dimension for interpreting N64 coordinates, then scale viewport/scissor and multiply vertex positions into the real window, with an aspect-ratio correction on X for widescreen. Texture formats are converted CPU-side into RGBA/bGRA GPU textures per `G_IM_FMT_*`/`G_IM_SIZ_*`. LUS additionally has explicit **framebuffer objects, framebuffer-to-texture binds, and custom "wide" display-list commands** for widescreen HUD/rects.

### Cited Findings
- Native dimensions are 320×240: LUS `#define SCREEN_WIDTH 320 / #define SCREEN_HEIGHT 240` with the comment "TODO figure out why changing these to 640x480 makes the game only render in a quarter of the window", and `mNativeDimensions.width/height` initialised to them via `SetNativeDimensions`/`Init` — [LUS `include/fast/interpreter.h`](https://github.com/HarbourMasters/libultraship/blob/main/include/fast/interpreter.h); [LUS `interpreter.cpp`](https://github.com/HarbourMasters/libultraship/blob/main/src/fast/interpreter.cpp).
- sm64ex: `SCREEN_WIDTH/SCREEN_HEIGHT` + `HALF_SCREEN_WIDTH`/`HALF_SCREEN_HEIGHT`; `#define RATIO_X (gfx_current_dimensions.width / (2.0f * HALF_SCREEN_WIDTH))` and `RATIO_Y`; the viewport is computed from the N64 `Vp_t` (2 fractional bits) and multiplied by `RATIO_X/Y`, then `gfx_adjust_x_for_aspect_ratio(x) = x * (4.0f/3.0f) / (width/height)` is applied to vertex X and rectangle X for widescreen — [sm64ex `gfx_pc.c`, `gfx_calc_and_set_viewport`, `gfx_adjust_x_for_aspect_ratio`, `gfx_sp_vertex`](https://github.com/sm64pc/sm64ex/blob/master/src/pc/gfx/gfx_pc.c).
- LUS mirrors this with `RATIO_X(activeFb, dims)`/`RATIO_Y`, `AdjXForAspectRatio`, `AdjustVIewportOrScissor`, `AdjustWidthHeightForScale`, and a `GfxDimensions { float internal_mul; uint32_t width, height; float aspect_ratio; }` — [LUS `interpreter.h`](https://github.com/HarbourMasters/libultraship/blob/main/include/fast/interpreter.h); [LUS `interpreter.cpp`](https://github.com/HarbourMasters/libultraship/blob/main/src/fast/interpreter.cpp).
- LUS exposes runtime scaling controls: `SetNativeDimensions(float,float)`, `SetResolutionMultiplier(float)`, `SetMsaaLevel(uint32_t)`, `GetCurDimensions(...)`, `AdjustPixelDepthCoordinates(float&,float&)` — [LUS `interpreter.h`](https://github.com/HarbourMasters/libultraship/blob/main/include/fast/interpreter.h).
- **Widescreen is partly done in display lists** via custom commands: `OTR_G_TEXRECT_WIDE (0x37)`, `OTR_G_FILLWIDERECT (0x38)`, `RDP_G_LOADBLOCK_WIDE (0x47)`, `RDP_G_VTX_WIDE (0x48)`, `RDP_G_TRI1_WIDE (0x49)` — [LUS `lus_gbi.h`](https://github.com/HarbourMasters/libultraship/blob/main/include/fast/lus_gbi.h); handlers `gfx_tex_rect_wide_handler_custom`, `gfx_fill_wide_rect_handler_custom` — [LUS `interpreter.cpp`, `otrHandlers`](https://github.com/HarbourMasters/libultraship/blob/main/src/fast/interpreter.cpp). (These let HUD/2D rects stretch to the wider viewport instead of being clamped to 4:3.)
- **Framebuffers are modelled as first-class GPU objects** in LUS: `struct FBInfo { uint32_t orig_width, orig_height; uint32_t applied_width, applied_height; uint32_t native_width, native_height; bool resize; bool forceFixedAspect; };` and APIs `CreateFrameBuffer`, `SetFrameBuffer(int, float noiseScale)`, `CopyFrameBuffer(int dst, int src, bool copyOnce, bool* hasCopied)`, `ResetFrameBuffer`, `RegisterFbTexture(const void* cpuAddr, int fbId)`, `UnregisterFbTexture` — [LUS `interpreter.h`](https://github.com/HarbourMasters/libultraship/blob/main/include/fast/interpreter.h). The comment for `RegisterFbTexture` is explicit about the boundary: "Register a CPU address as a mirror of a GPU framebuffer texture. When ImportTexture encounters this address, it uses SelectTextureFb instead of reading from CPU memory — giving full GPU resolution with no readback." — [LUS `interpreter.h`](https://github.com/HarbourMasters/libultraship/blob/main/include/fast/interpreter.h).
- Framebuffer-related GBI commands: `G_SETFB`, `G_RESETFB`, `G_SETTIMG_FB`, `G_COPYFB`, `G_READFB`, `G_IMAGERECT`, `G_LOADBLOCK_WIDE` — [LUS `lus_gbi.h`](https://github.com/HarbourMasters/libultraship/blob/main/include/fast/lus_gbi.h); handler names `gfx_set_fb_handler_custom`, `gfx_copy_fb_handler_custom`, `gfx_read_fb_handler_custom`, `gfx_set_timg_fb_handler_custom` — [LUS `interpreter.cpp`](https://github.com/HarbourMasters/libultraship/blob/main/src/fast/interpreter.cpp).
- **Texture format conversion** — sm64ex decodes all standard N64 formats CPU-side into RGBA32 and uploads: `import_texture_rgba32`, `import_texture_rgba16` (5-5-5-1 → 8-8-8-8 via `SCALE_5_8`), `import_texture_ia4`, `import_texture_ia8`, `import_texture_ia16`, `import_texture_i4`, `import_texture_i8`, `import_texture_ci4`, `import_texture_ci8` (palette lookup big-endian); unsupported format/size → `sys_fatal("unsupported … texture size/format")` — [sm64ex `gfx_pc.c`](https://github.com/sm64pc/sm64ex/blob/master/src/pc/gfx/gfx_pc.c).
- LUS has the same set plus HD replacement texturing: `ImportTextureRgba16/Rgba32/IA4/IA8/IA16/I4/I8/Ci4/Ci8`, plus `ImportTextureRaw`/`ImportTextureImg` with `RawTexMetadata { width, height, h_byte_scale, v_pixel_scale, resource, type }` for HD/imported textures; CI4 uses multi-palette staging `palette_staging[2][256]` and `palettes[16]`; `G_TX_CLAMP`/mask handling trims over-loaded textures — [LUS `interpreter.cpp`, `ImportTexture*`](https://github.com/HarbourMasters/libultraship/blob/main/src/fast/interpreter.cpp); [LUS `interpreter.h`, `RDP`/`RawTexMetadata`](https://github.com/HarbourMasters/libultraship/blob/main/include/fast/interpreter.h).
- Texture-format enum source of truth: `G_IM_FMT_RGBA/YUV/CI/IA/I` and `G_IM_SIZ_4b/8b/16b/32b` — [LUS `gbi.h`](https://github.com/HarbourMasters/libultraship/blob/main/include/libultraship/libultra/gbi.h); [Hack64 `G_SETTIMG`/`G_SETTILE`](https://hack64.net/wiki/doku.php?id=super_mario_64:fast3d_display_list_commands). LUS's `interpreter.cpp` includes a `G_IM_FMT_YUV` branch (line region ~1406) — YUV exists in the switch.
- Z-buffer/back-end format differences are handled by a back-end query `z_is_from_0_to_1()` and a conversion `z = (z + w) / 2.0f` for 0..1 depth APIs (D3D) — [sm64ex `gfx_pc.c`, `gfx_sp_tri1`](https://github.com/sm64pc/sm64ex/blob/master/src/pc/gfx/gfx_pc.c); the back-end interface is [sm64ex `gfx_rendering_api.h`](https://github.com/sm64pc/sm64ex/blob/master/src/pc/gfx/gfx_rendering_api.h).
- Back-ends / windowing: LUS "Supports OpenGL, Direct3D 11, and Metal backends" ([LUS Porting Guide](https://libultraship.com/PORTING)); SoH lists "DirectX11 (Windows), OpenGL (all platforms), and Metal (MacOS)… change which API to use in the `Settings` menu" ([Shipwright README](https://github.com/HarbourMasters/Shipwright)); sm64ex exposes GL2.1/GL1.3/D3D11/D3D12 ([sm64ex README](https://github.com/sm64pc/sm64ex)).

### Inferences
- The design principle is "the game renders at 320×240 in N64 coordinate space; the port scales the mapping to the window." Widescreen is achieved by widening the aspect ratio on X (and by special wide display-list commands for 2D HUD), not by changing the game's projection math in the game source — which is why it can be toggled.
- Framebuffer-as-texture (`RegisterFbTexture`, `G_READFB`) exists specifically to avoid CPU readback; this is the analogue of an eidos "render target read by the game" (e.g. DS sub-screen/3D-on-BG effects).

### Gaps
- I did not verify how SoH surfaces the resolution-multiplier / MSAA UI options (option names, defaults) beyond the API surface in `interpreter.h`.
- YUV decoding fidelity in LUS was not read in detail (only the presence of a `G_IM_FMT_YUV` branch confirmed).

## Q6. Is there a stated boundary between "console-shaped state" and "native rendering"? Quote any doc that draws it.

### Takeaway
There is **no doc that uses the exact framing "console-shaped state vs native rendering."** However, the boundary is drawn explicitly and consistently in prose in three places: LUS as "compile-time WINE" / "header-compatible wrapper around modern reimplementations of N64 SDK functions"; the renderer directory described as "Interprets N64 display lists as commands for modern GPUs"; and the split between a libultra layer (`src/libultraship/`) and a platform-agnostic/native layer (`src/ship/`, `src/fast/backends/`). I quote them verbatim below.

### Cited Findings
- **The clearest statement of the boundary (LUS Porting Guide):** "It is not a recompilation tool; rather, it allows developers to build a game's original source code (derived from decompilation) on modern hardware by providing a header-compatible wrapper around modern reimplementations of N64 SDK functions. In essence, LUS acts as '**compile-time WINE**' for the N64." — [LUS Porting Guide](https://libultraship.com/PORTING).
- **Renderer boundary (LUS Porting Guide directory table):** "`src/fast/` | The Fast3D Renderer. **Interprets N64 display lists as commands for modern GPUs.** Supports OpenGL, Direct3D 11, and Metal backends."; and "`src/libultraship/` | Contains N64-specific code including the libultra reimplementation (`libultra/`), bridge layers to modern backends (`bridge/`)…"; "`src/ship/` | **Platform-agnostic code**: resource/archive management, audio backends (SDL, CoreAudio, WASAPI), controller abstractions, configuration…" — [LUS Porting Guide](https://libultraship.com/PORTING).
- **Renderer boundary (LUS `src/fast/README.md`):** "Nintendo 64 Fast3D renderer — Implementation of a Fast3D renderer for games built originally for the Nintendo 64 platform. For rendering, OpenGL, Direct3D 11, and Metal are supported. Supported windowing systems are DXGI (used on Windows) and SDL (generic)." — [LUS `src/fast/README.md`](https://github.com/HarbourMasters/libultraship/blob/main/src/fast/README.md).
- **SDK-vs-hardware boundary (LUS README):** "libultraship (LUS) is a library meant to provide reimplementations of libultra (n64 sdk) functions that run on modern hardware." — [LUS README](https://github.com/HarbourMasters/libultraship/blob/main/README.md).
- **SDK-vs-hardware boundary (Harbour Masters):** "LibUltraShip (LUS) is our modern recreation of the Nintendo 64 SDK, known as LibUltra. It provides the foundation for all our ports, handling graphics, audio, input, and core game systems." and "We build upon decompilation projects once they reach completion, recreating the original game code in modern C++…" — [Harbour Masters About](https://www.harbourmasters.org/about).
- **Concrete boundary artefact (`RegisterFbTexture` comment):** "Register a CPU address as a mirror of a GPU framebuffer texture. When ImportTexture encounters this address, it uses SelectTextureFb instead of reading from CPU memory — giving full GPU resolution with no readback." — [LUS `include/fast/interpreter.h`](https://github.com/HarbourMasters/libultraship/blob/main/include/fast/interpreter.h).
- Harbour Masters describes the porting workflow as building on completed decompilations rather than reimplementing the game: "We build upon decompilation projects once they reach completion, recreating the original game code in modern C++ and enhancing it with new features." — [Harbour Masters About](https://www.harbourmasters.org/about).

### Inferences
- The boundary the ports actually draw is: **"N64-shaped input" = a Gfx command stream + libultra API calls** (console-shaped, game-visible), and **"native output" = GPU draw calls emitted through `GfxRenderingAPI`** (backend-specific). The interpreter is the membrane between them, and `RenderingState` (the cached GPU state) is the native-side shadow.
- For eidos this is the reusable lesson: define a *console-shaped input contract* (here: register writes / command-buffer words) and a *native output contract* (draw calls), with the emulation layer as the only place that knows N64/NDS specifics — and keep the game's C on the console-shaped side.

### Gaps
- No primary doc uses the phrase "console-shaped state" or draws a formal diagram of "console state ↔ native rendering." The above quotes are the closest authored statements I could verify. If a formal statement exists, it is likely in a talk/blog or the DeepWiki summary rather than in-tree docs (the DeepWiki "Engine Architecture" page returned HTTP 429 on two fetch attempts and was not read).

## Q7. Compare libultraship's renderer architecture to a plain reimplementation (where the port reimplements a high-level draw call instead of interpreting the command stream)

### Takeaway
libultraship's Fast3D is a **command-stream interpreter with an emulated RSP/RDP state machine and generated-shader combiner**, not a "draw call" reimplementation. The consequence is that it preserves the game's *entire, runtime-generated* display-list vocabulary and needs no per-scene asset conversion for geometry; the cost is that fidelity is bounded by how completely the interpreter models the RDP, and unsupported commands/features degrade (log-and-skip / approximation). A plain reimplementation would instead re-implement specific draw paths (and convert assets) and would break on dynamically generated display lists and modifiers.

### Cited Findings
- libultraship's renderer maintains hardware state and decodes every command: `RSP`/`RDP` structs + `gfx_step()` opcode dispatch + `GfxSpMatrix/GfxSpVertex/GfxSpTri1/GfxDp*` handlers — [LUS `include/fast/interpreter.h`](https://github.com/HarbourMasters/libultraship/blob/main/include/fast/interpreter.h); [LUS `interpreter.cpp`](https://github.com/HarbourMasters/libultraship/blob/main/src/fast/interpreter.cpp).
- The native side is abstracted behind one interface, so the *same* interpreter drives OpenGL/D3D11/Metal: the porting guide states `src/fast/` "Interprets N64 display lists as commands for modern GPUs. Supports OpenGL, Direct3D 11, and Metal backends." — [LUS Porting Guide](https://libultraship.com/PORTING). The back-end interface is `GfxRenderingAPI` (methods such as `DrawTriangles`, `UploadTexture`, `SelectTexture`, `SetSamplerParameters`, `CreateAndLoadNewShader`, `StartDrawToFramebuffer`) referenced throughout `interpreter.cpp`/`interpreter.h`.
- Because it consumes raw words, it supports **runtime-generated display lists** (the same reason the decompilation guide can translate dynamic `temp->unk0/unk4` writes into `gDP*`/`gSP*` macros and still have them execute): dynamic command patterns exist and are executed — [HackMD, "Dynamic (Code) commands"](https://hackmd.io/@Roman971/Hk01jRxRr).
- The trade-off is visible in the approximations and in the custom-command escape hatches: LOD is faked (`distance_frac = (w - 3000)/3000`), coverage/AA bits are ignored, unknown commands are skipped, and features the interpreter can't express in classic GBI are added as custom opcodes (`G_TEXRECT_WIDE`, `G_READFB`, `G_PUSH_SHADER`, …) — [sm64ex `gfx_pc.c`](https://github.com/sm64pc/sm64ex/blob/master/src/pc/gfx/gfx_pc.c); [LUS `interpreter.cpp`](https://github.com/HarbourMasters/libultraship/blob/main/src/fast/interpreter.cpp); [LUS `lus_gbi.h`](https://github.com/HarbourMasters/libultraship/blob/main/include/fast/lus_gbi.h).
- A "conversion" path is offered only for **assets** (Torch swaps C files to path references; OTR/O2R archives), not for the renderer — reinforcing that geometry/rendering is interpreted, not re-described — [LUS Porting Guide, Phase 3](https://libultraship.com/PORTING); [LUS README](https://github.com/HarbourMasters/libultraship/blob/main/README.md).
- Upstream lineage confirms this is one architecture shared across ports: Emill's `n64-fast3d-engine` ("Implementation of a Fast3D renderer for games built originally for the Nintendo 64 platform") is the ancestor of sm64ex's `gfx_pc.c` and of LUS's `src/fast/` — [Emill/n64-fast3d-engine](https://github.com/Emill/n64-fast3d-engine); [sm64ex README](https://github.com/sm64pc/sm64ex).

### Inferences
- **Plain-reimplementation cost:** if eidos reimplemented a high-level draw call (e.g. "draw sprite on BG") it would have to reproduce the DS 2D/3D engine's exact behaviour for every caller and would need the game's rendered command/data to be converted per-case; it would not execute the game's dynamically computed register values or command streams. The interpreter approach defers all of that to one central engine that consumes the same words the console's hardware would. This is the pattern eidos is already adopting (register file + 2D/3D engine drawing from hardware state).
- **Where the N64 ports are strictly easier than the NDS case:** N64 GBI is a *forward-only command stream with no readback*, so the ports never needed a readable memory-mapped register file. DS hardware (DISPCNT/VRAM/OAM/palette, BG/OBJ registers, and read-back via `DISPSTAT`/`VCOUNT`) is closer to a memory-mapped peripheral, so eidos's "register file with write hooks" is a superset of what the N64 ports implemented. The N64 precedent validates the *engine-from-state* half of eidos's design, not the *register file* half.

### Gaps
- I did not read an example of a port that *did* choose high-level reimplementation, so the "plain reimplementation" side of the comparison is reasoned from the architecture rather than cited from a concrete N64 counterexample.
- RT64 (used by sm64coopdx/Render96 for ray tracing) is also an interpreter-style renderer but with much higher fidelity; I mention it only because it appears in current SM64-port docs ([sm64ex/RT64 usage](https://www.pcgamingwiki.com/wiki/Super_Mario_64_(sm64ex))) and did not fetch its source, so any RT64-specific fidelity claim is out of scope here.
